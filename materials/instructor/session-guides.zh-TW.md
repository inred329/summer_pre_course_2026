# 前導課程教師執行指引

版本：0.3.0  
狀態：正式執行草案  
最後更新：2026-08-10  
重大變更摘要：補齊英文班五堂完整執行安排，使其與中文班具有相同層級的核心問題、時間表、作業討論、代表性錯誤與備援取捨；保留錯誤 AI 建議作為可選驗證素材，不安排固定 AI 驗證時段或要求學生保存 AI 使用紀錄。  
對應英文版本：[Preparatory Course Instructor Implementation Guide](session-guides.en.md)

## 文件用途

供教師與助教直接執行前導課程。本文負責節奏、作業討論、參與觀察、代表性錯誤與備援策略；不定義最終口試的完整題型與流程，也不把教師行政內容放回學生教材。

## 共同授課循環

除第一堂外，每堂原則上依下列順序：

```text
前次作業討論 15–25 分鐘
→ 本堂核心問題
→ 視覺模型與執行前預測
→ 最小可執行範例
→ 引導修改、測試與除錯
→ 課堂整理
→ 指定下一份自主作業
```

作業不繳交、不計分。學生自行保存程式、測試、追蹤、錯誤與修改紀錄；不要求固定使用 AI 或保存 AI 對話。

## AI 在教師指引中的定位

- AI 不是獨立課程主題，也不占固定時段。
- 教師可視學生誤解，選用一則「看似合理但錯誤」的 AI 建議作為一般錯誤案例。
- 使用時仍遵守：先預測，再以程式、編譯器、追蹤或測試驗證。
- 學生未使用 AI 不影響參與或評量。
- 不要求學生提出 AI 使用紀錄、未使用聲明或固定格式反思。

## 課堂參與觀察

可觀察證據包括：

- 提出具體問題或說明卡點。
- 回答、修正或補充推理。
- 參與程式追蹤、測試、除錯或解法比較。
- 分享自己犯過的錯誤。
- 提出正常、邊界或異常測試。
- 透過書面、匿名提問、程式操作或小組紀錄參與。

不得以出席、點名、發言次數或反應速度取代參與判定。

# 中文班四堂執行安排

## 第 1 堂：執行模型與第一個程式（180 分鐘）

### 核心問題

> 人類寫下的 C 原始碼，如何成為電腦實際執行的行為？

### 建議時間

| 時間 | 活動 |
|---:|---|
| 0–20 | 課程制度：不點名、作業不繳、課堂參與與最終口試 |
| 20–45 | 原始碼、編譯器、可執行檔與執行流程圖 |
| 45–70 | 預測並執行最小程式 |
| 70–90 | 漏分號等編譯錯誤診斷 |
| 90–100 | 休息 |
| 100–130 | 修改程式但不重新編譯的實驗 |
| 130–160 | 值、變數與第一個狀態追蹤 |
| 160–175 | 學生操作與分享錯誤 |
| 175–180 | 指定自主作業 1 |

### 必備錯誤案例

- 漏分號造成編譯失敗。
- 修改原始碼但執行舊可執行檔。
- 把「編譯成功」誤認為「程式已執行且正確」。

### 可選的外部建議案例

> 「修改 `.c` 檔後直接執行舊的 `.exe`，作業系統會自動讀取最新原始碼。」

不論建議來自 AI、搜尋結果或同儕，學生都先預測，再透過修改輸出文字、執行舊檔與重新編譯驗證。

### 時間不足時

保留工具鏈、預測、漏分號錯誤與重新編譯實驗；縮短自由練習。

## 第 2 堂：資料、型別與狀態（180 分鐘）

### 前次作業討論

優先討論：

- 編譯與執行的差異。
- 為何修改後必須重新編譯。
- 學生自行製造的錯誤。

### 核心問題

> 程式如何記住資料、改變資料，並讓我們確認結果合理？

### 建議時間

| 時間 | 活動 |
|---:|---|
| 0–25 | 作業 1 討論與匿名錯誤案例 |
| 25–55 | 值、型別、變數、初始化與指定 |
| 55–85 | 狀態追蹤表與手算 |
| 85–95 | 休息 |
| 95–125 | `scanf`、處理與輸出 |
| 125–150 | 整數除法與格式型別錯誤 |
| 150–170 | 需求修改與回歸測試 |
| 170–180 | 指定自主作業 2 |

### 必備錯誤案例

```c
int total = 5;
int count = 2;
double average = total / count;
```

另準備 `%d`、`%lf` 與變數型別不一致的案例。

### 可選的外部建議案例

> 「只要左邊是 `double`，右邊的整數除法就一定會保留小數。」

要求學生先手算，再執行 `5 / 2` 與 `5.0 / 2` 比較。

## 第 3 堂：條件、迴圈與終止（180 分鐘）

### 前次作業討論

優先討論：

- 型別選擇。
- 狀態表與實際程式不一致的位置。
- 滿額免運等需求修改的測試。

### 核心問題

> 程式如何選擇路徑並可靠地重複工作？

### 建議時間

| 時間 | 活動 |
|---:|---|
| 0–25 | 作業 2 討論 |
| 25–55 | 條件與路徑模型 |
| 55–85 | 邊界案例與條件順序 |
| 85–95 | 休息 |
| 95–125 | 迴圈四要素與逐次追蹤 |
| 125–150 | off-by-one 與無窮迴圈診斷 |
| 150–170 | 有效成績統計器修改與測試 |
| 170–180 | 指定自主作業 3 |

### 必備錯誤案例

- 把 `=` 寫成比較用途。
- 邊界使用 `<` 而非 `<=`。
- 迴圈忘記更新控制變數。
- 結束標記也被加入統計。

### 可選的外部建議案例

> 「迴圈只要有 `break` 就不可能成為無窮迴圈。」

學生找出 `break` 永遠無法執行的反例。

## 第 4 堂：函數、責任分解與整合（180 分鐘）

### 前次作業討論

優先討論：

- 終止條件與更新順序。
- off-by-one 錯誤。
- 零筆有效資料的處理。

### 核心問題

> 如何把小型需求分解、實作、測試、修改並建立可信證據？

### 建議時間

| 時間 | 活動 |
|---:|---|
| 0–25 | 作業 3 討論 |
| 25–55 | 函數責任與介面圖 |
| 55–85 | 呼叫、參數與回傳值追蹤 |
| 85–95 | 休息 |
| 95–130 | 重構過大的 `main` |
| 130–160 | 整合作業、需求修改與回歸測試 |
| 160–175 | 比較分解方案或診斷一則外部建議 |
| 175–180 | 作業整理與最終口試準備原則 |

### 必備錯誤案例

- 函數宣告回傳值但沒有 `return`。
- 呼叫端忽略回傳值。
- 函數名稱與責任不一致。
- 需求修改後只測新功能，未回歸舊功能。

### 可選的外部建議案例

> 「將所有變數改成全域變數，可以讓函數分解更簡單，因此是初學者最好的解法。」

學生比較全域狀態與參數／回傳值的可追蹤性和測試性。

# 英文班五堂執行安排

英文班每堂 120 分鐘，總時數與中文班相同。除 Session 1 外，每堂保留約 15–20 分鐘討論前次自主作業，再進入本堂核心任務。英文班可使用術語卡、句型支架、書面回答與成對討論降低語言負荷，但核心任務、推理要求與驗證標準不因授課語言而降低。

## Session 1：執行模型與第一個程式（120 分鐘）

### 核心問題

> 人類寫下的 C 原始碼，如何經過工具鏈成為電腦實際執行的行為？

### 建議時間

| 時間 | 活動 |
|---:|---|
| 0–15 | 課程制度：不點名、作業不繳、課堂參與與最終口試 |
| 15–35 | 原始碼、編譯器、可執行檔與執行流程圖 |
| 35–55 | 預測並執行最小程式 |
| 55–75 | 漏分號、拼字與編譯錯誤診斷 |
| 75–85 | 休息 |
| 85–105 | 修改原始碼但不重新編譯的實驗 |
| 105–115 | 學生操作、口頭或書面說明觀察結果 |
| 115–120 | 指定自主作業 1 |

### 必備錯誤案例

- 漏分號造成編譯失敗。
- 修改原始碼但執行舊可執行檔。
- 把「編譯成功」誤認為「程式已正確執行」。

### 可選的外部建議案例

> 「修改 `.c` 檔後直接執行舊的 `.exe`，作業系統會自動讀取最新原始碼。」

學生先預測，再透過修改輸出文字、執行舊檔與重新編譯驗證。教師可要求學生用一句簡短英文說明 `source code`、`compiler`、`executable` 三者的關係，也可接受流程圖或書面回答。

### 時間不足時

保留工具鏈、預測、漏分號錯誤與重新編譯實驗；縮短自由操作與分享。

## Session 2：資料、型別與程式狀態（120 分鐘）

### 前次作業討論

優先討論：

- 編譯與執行的差異。
- 為何修改後必須重新編譯。
- 學生自行製造的錯誤與診斷方式。

### 核心問題

> 程式如何保存、改變與輸入資料？我們如何追蹤狀態並判斷結果是否合理？

### 建議時間

| 時間 | 活動 |
|---:|---|
| 0–20 | 作業 1 討論與匿名錯誤案例 |
| 20–40 | 值、型別、變數、初始化與指定 |
| 40–60 | 狀態追蹤表與執行前手算 |
| 60–70 | 休息 |
| 70–90 | `scanf`、資料處理與輸出 |
| 90–108 | 整數除法、格式型別與常見錯誤 |
| 108–116 | 小型需求修改與回歸測試 |
| 116–120 | 指定自主作業 2 |

### 必備錯誤案例

```c
int total = 5;
int count = 2;
double average = total / count;
```

另準備 `%d`、`%lf` 與變數型別不一致，以及未初始化變數的簡短案例。

### 可選的外部建議案例

> 「只要左邊是 `double`，右邊的整數除法就一定會保留小數。」

學生先填寫預測值，再執行 `5 / 2` 與 `5.0 / 2` 比較。若語言表達形成負擔，可提供句型：`I expected ___, but the program produced ___ because ___.`

### 時間不足時

保留狀態追蹤、`scanf`、整數除法與一個格式錯誤；需求修改可移入自主作業。

## Session 3：條件、迴圈與終止（120 分鐘）

### 前次作業討論

優先討論：

- 型別選擇與輸入格式。
- 狀態表與實際執行不一致的位置。
- 修改需求後有哪些舊案例需要重新測試。

### 核心問題

> 程式如何選擇路徑、重複工作，並確保迴圈會在正確時機停止？

### 建議時間

| 時間 | 活動 |
|---:|---|
| 0–20 | 作業 2 討論 |
| 20–40 | 條件、布林判斷與路徑模型 |
| 40–58 | 邊界案例與條件順序 |
| 58–68 | 休息 |
| 68–90 | 迴圈四要素與逐次追蹤 |
| 90–108 | off-by-one、無窮迴圈與 sentinel 診斷 |
| 108–116 | 有效資料統計器修改與測試 |
| 116–120 | 指定自主作業 3 |

### 必備錯誤案例

- 把 `=` 寫成比較用途。
- 邊界使用 `<` 而非 `<=`。
- 迴圈忘記更新控制變數。
- 結束標記也被加入統計。

### 可選的外部建議案例

> 「迴圈只要有 `break` 就不可能成為無窮迴圈。」

學生設計或找出 `break` 永遠無法執行的反例，並用追蹤表說明原因。可讓學生先成對討論，再由教師收集兩種不同錯誤路徑。

### 時間不足時

保留條件邊界、迴圈四要素、off-by-one 與無窮迴圈；縮短統計器的自由修改。

## Session 4：函數、參數、回傳值與責任分解（120 分鐘）

### 前次作業討論

優先討論：

- 終止條件與更新順序。
- off-by-one 錯誤。
- 零筆有效資料或特殊輸入時的處理。

### 核心問題

> 如何把一段程式拆成可理解、可追蹤、可測試的小責任？

### 建議時間

| 時間 | 活動 |
|---:|---|
| 0–20 | 作業 3 討論 |
| 20–40 | 函數責任、函數名稱與介面圖 |
| 40–60 | 參數、區域變數與回傳值追蹤 |
| 60–70 | 休息 |
| 70–92 | 從過大的 `main` 抽出第一個函數 |
| 92–108 | 比較兩種分解方式並設計單獨測試 |
| 108–116 | 診斷函數相關錯誤 |
| 116–120 | 指定自主作業 4 |

### 必備錯誤案例

- 函數宣告回傳值但沒有 `return`。
- 呼叫端忽略回傳值。
- 參數與區域變數的責任混淆。
- 函數名稱與實際責任不一致。

### 可選的外部建議案例

> 「將所有變數改成全域變數，可以讓函數分解更簡單，因此是初學者最好的解法。」

學生比較全域狀態與參數／回傳值兩種寫法，從「能否單獨測試」「能否追蹤資料來源」「修改是否影響其他函數」三個角度驗證。

### 時間不足時

保留函數責任、參數／回傳值追蹤與一次實際重構；分解方案比較可移至 Session 5 開場。

## Session 5：整合、需求修改、回歸測試與學習整理（120 分鐘）

### 前次作業討論

優先討論：

- 函數責任是否單一。
- 參數與回傳值是否足以追蹤資料流。
- 重構後原有功能是否仍正確。

### 核心問題

> 當需求改變時，如何修改一個已能執行的程式，並建立足夠證據證明新舊功能都可靠？

### 建議時間

| 時間 | 活動 |
|---:|---|
| 0–20 | 作業 4 討論與函數分解比較 |
| 20–40 | 整合題需求閱讀、責任分解與測試清單 |
| 40–60 | 先完成基線版本並建立正常／邊界案例 |
| 60–70 | 休息 |
| 70–92 | 教師公布需求變更，學生修改程式 |
| 92–108 | 回歸測試：新功能與舊功能一起驗證 |
| 108–116 | 分享失敗案例、比較證據與除錯策略 |
| 116–120 | 作業整理與最終口試準備原則 |

### 必備錯誤案例

- 需求修改後只測新功能，未重測原有案例。
- 為了快速完成修改，把原本的函數責任重新混回 `main`。
- 修正一個邊界條件後破壞另一個既有情境。
- 只憑「看起來有跑」判定程式正確，沒有具體測試輸入與預期輸出。

### 可選的外部建議案例

> 「既然新增功能的測試已經通過，就不需要重新測試原本功能。」

學生以同一份程式建立至少一個新功能案例與兩個既有案例，實際驗證回歸測試的必要性。

### 時間不足時

保留需求變更、至少三個回歸案例與學習整理；縮短成果分享，不縮減實際測試。

## 英文班語言支架原則

英文班的差異在語言支援，不在程式設計認知要求。教師可使用：

- 關鍵術語卡：source code、compiler、executable、variable、type、condition、loop、function、parameter、return value、test case、boundary case。
- 句型支架，例如：`I predict ___ because ___.`、`The bug occurs when ___.`、`This test checks ___.`。
- 先書面再口頭、先成對再全班的回答方式。
- 允許學生用流程圖、追蹤表、程式輸出與測試結果補足口語表達。

不得因英文口語速度較慢而降低追蹤、預測、測試、除錯與需求修改的要求，也不得把英文流暢度當成程式設計能力的替代指標。

## 備援環境

- 教師預先測試的 GCC／Clang C17 環境。
- 無法使用個人設備時，以教師設備、成對操作或紙上追蹤完成核心活動。
- 工具故障不得直接視為未參與或能力不足。

## 課後教師紀錄

每堂只需記錄：

- 本堂主要誤解。
- 有效的錯誤案例。
- 學生普遍卡點。
- 需要下堂延續的問題。
- 課堂參與的整體趨勢與少量代表性證據。

不得建立逐次點名表、固定 AI 使用表或以每次發言累積分數。
