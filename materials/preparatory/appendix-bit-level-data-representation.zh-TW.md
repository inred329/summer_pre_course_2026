# P-U02 選讀附錄：資料在位元層級是怎麼表示的？

版本：1.0.0  
狀態：選讀學生附錄  
最後更新：2026-08-11  
對應英文版本：[P-U02 Optional Appendix: How Is Data Represented at the Bit Level?](appendix-bit-level-data-representation.en.md)

P-U02 的主線把注意力放在「值、型別、變數與狀態」：

```text
score 目前保存 80
→ 執行指定
→ score 變成 85
```

但如果再往下一層問：

> `80`、`-5`、`5.75` 或 `'A'` 真正放進記憶體時，到底長什麼樣？

答案會走到 **bit（位元）層級的資料表示**。

這份附錄是選讀。你不需要先理解它才能繼續 P-U03。它的用途是幫你建立一個更底層的直覺：**電腦最後保存的是位元模式，而型別決定這些位元要怎麼被解讀與操作。**

---

## 1. 先把「值」和「位元模式」分開

一個 bit 只有兩種狀態：

```text
0
1
```

多個 bit 排在一起，就可以形成很多不同模式。

例如 8 個 bit 可以形成：

```text
00000000
00000001
00000010
...
11111111
```

總共有：

```text
2^8 = 256
```

種不同模式。

但位元模式本身不會自動告訴你「我是整數」、「我是負數」或「我是字元」。

例如：

```text
01000001
```

如果把它當成無號二進位整數，可以得到十進位 65；在常見 ASCII 環境中，它也剛好可以對應字元 `A`。

所以真正重要的問題不是只有：

> 這些 bits 是什麼？

還要問：

> 我現在用什麼型別與表示規則去解讀它？

這就是 P-U02 所說「型別會影響值怎麼表示、怎麼運算」的底層版本。

---

## 2. byte 不一定等於「永遠 8 bits」

在 C 裡：

```c
sizeof(char) == 1
```

一定成立。

但 C 語言中的一個 byte 含多少 bit，要看：

```c
CHAR_BIT
```

它定義在：

```c
#include <limits.h>
```

常見機器上：

```text
CHAR_BIT = 8
```

所以日常常說「1 byte = 8 bits」。但嚴格來說，C 保證的是 `CHAR_BIT >= 8`，不是所有實作永遠剛好 8。

這份附錄為了方便畫圖，接下來大量使用 **8-bit 教學模型**。看到 8 bits 時，先把它當成理解表示法的模型，不要立刻推論 `int` 在所有 C 環境都只有 8 bits。

---

## 3. 無號整數：每一個位置有自己的權重

先從最單純的 unsigned binary integer 開始。

8 bits：

```text
位置:   7   6   5   4   3   2   1   0
權重: 128  64  32  16   8   4   2   1
```

例如：

```text
00001101
```

可以算成：

```text
8 + 4 + 1 = 13
```

所以：

```text
00001101₂ = 13₁₀
```

8-bit 無號整數能表示：

```text
00000000 = 0
...
11111111 = 255
```

也就是：

```text
0 ～ 2^8 - 1
```

一般化來說，如果有 `N` 個 bits 都拿來表示無號數，範圍就是：

```text
0 ～ 2^N - 1
```

---

## 4. 那負數要怎麼放進 bits？

只看 unsigned 時，所有 bit pattern 都已經拿來表示 0 或正數。

如果還要表示負數，就需要另一套規則。

現代電腦最常見的做法是 **two's complement（二補數／二的補數）**。

先用 8-bit 模型看：

```text
00000101 = +5
```

要得到 `-5` 的二補數表示，可以用一個常見計算方式：

### 第一步：先寫出 +5

```text
00000101
```

### 第二步：每個 bit 反轉

```text
11111010
```

### 第三步：再加 1

```text
11111010
+       1
----------
11111011
```

所以在 8-bit two's-complement 模型裡：

```text
+5 = 00000101
-5 = 11111011
```

---

## 5. 為什麼二補數很適合做加法？

看看：

```text
  00000101   (+5)
+ 11111011   (-5)
-----------
1 00000000
```

如果我們只有 8 個位置，最左邊多出來的 carry 不留在這 8 bits 中，剩下：

```text
00000000
```

就是 0。

這個特性讓同一套二進位加法電路可以自然處理很多正負數運算，不需要為「負數加法」另外發明完全不同的規則。

---

## 6. 二補數也可以用「最高位是負權重」來讀

8-bit two's complement 還可以這樣理解：

```text
bit:      7    6   5   4   3   2   1   0
weight: -128  64  32  16   8   4   2   1
```

例如：

```text
11111011
```

可以讀成：

```text
-128 + 64 + 32 + 16 + 8 + 2 + 1
= -5
```

這個角度常常比每次「反轉再加一」更容易直接判讀。

---

## 7. 為什麼 8-bit 二補數是 -128 ～ 127？

8 bits 總共有 256 種模式。

在 two's-complement 規則中：

```text
00000000 ～ 01111111
```

表示：

```text
0 ～ 127
```

而：

```text
10000000 ～ 11111111
```

表示：

```text
-128 ～ -1
```

所以範圍是：

```text
-128 ～ 127
```

這裡有一個值得注意的非對稱：

```text
最大正數 = 127
最小負數 = -128
```

因此最小負數沒有對應的 `+128` 可以放進同一個 8-bit signed 範圍。

---

## 8. C17 和二補數：不要把「常見」說成「唯一」

這份課程的程式範例以 C17 為基準。

在 C17 中，**不能把所有 signed integer 實作都當成語言保證一定使用 two's complement**。歷史上 C 也容許其他 signed representation。

所以這份附錄使用 two's complement，是因為：

- 它是現代一般處理器上最重要、最常見的模型；
- 它能很好地解釋正負整數的位元運算；
- 你之後讀組合語言、機器層級資料時會一直遇到它。

但如果你在寫需要可攜性的 C 程式，不應只因為自己的電腦用二補數，就把某個 bit pattern 當成所有 C17 實作都保證有相同 signed 解讀。

同樣地，也不要直接背：

```text
int = 32 bits
```

C 的 `int` 實際大小與範圍要看實作。可以從：

```c
#include <limits.h>
```

查：

```text
INT_MIN
INT_MAX
CHAR_BIT
```

並用：

```c
sizeof(int)
```

觀察目前環境。

---

## 9. 浮點數不能只用「整數再加一個小數點」理解

現在看：

```c
double temperature = 5.75;
```

浮點數的目標不是固定把某幾個 bits 放在小數點左邊、某幾個放右邊。

它比較像科學記號。

十進位會寫：

```text
6.02 × 10^23
```

二進位浮點則可以寫成類似：

```text
1.xxxxx × 2^e
```

現代常見的 IEEE 754 binary floating-point 會把位元分成三個角色：

```text
sign | exponent | fraction
符號 | 指數     | 小數／有效數字部分
```

---

## 10. 用 IEEE 754 binary32 看 `5.75`

這一節使用常見的 IEEE 754 **binary32** 模型，也就是很多系統上的 32-bit `float`。

欄位分配是：

```text
1 bit   sign
8 bits  exponent
23 bits fraction
```

先把十進位 `5.75` 轉成二進位：

```text
5    = 101₂
0.75 = 0.11₂
```

所以：

```text
5.75 = 101.11₂
```

把它正規化：

```text
1.0111 × 2^2
```

因此：

```text
sign = 0
```

指數 `2` 在 binary32 會加上 bias 127：

```text
2 + 127 = 129
```

129 的二進位是：

```text
10000001
```

fraction 儲存正規化後小數點右側：

```text
01110000000000000000000
```

所以 `5.75` 的 binary32 bit pattern 是：

```text
0 | 10000001 | 01110000000000000000000
```

---

## 11. 負浮點數怎麼表示？

在 IEEE 754 這個例子裡，`-5.75` 的 magnitude 和 exponent 不需要重新做二補數。

主要差別是 sign bit：

```text
+5.75
0 | 10000001 | 01110000000000000000000

-5.75
1 | 10000001 | 01110000000000000000000
```

這是一個很重要的對比：

> **二補數是常見 signed integer 表示法；IEEE 754 浮點負數不是把整個 bit pattern 做二補數。**

不要把「負整數怎麼表示」的規則直接套到浮點數。

---

## 12. 為什麼 `0.1` 常常不能被精確保存？

十進位的：

```text
0.5
```

可以寫成：

```text
0.1₂
```

所以很容易精確表示。

但十進位 `0.1` 轉成二進位時會形成無限循環的小數。

有限的 fraction bits 裝不下無限多位，因此實際保存的是附近一個可表示的值。

這就是為什麼：

```c
0.1 + 0.2
```

的浮點結果，可能不是你想像中的「位元層級完全等於十進位 0.3」。

這不是浮點數隨機算錯，而是**表示能力本身有限**。

正式課程 F-U01 會再從「表示、型別與運算」角度深入這個問題。

---

## 13. IEEE 754 還有一些特殊 bit patterns

以 binary32 為例，exponent 欄位還會保留一些特殊規則，用來表示：

```text
+0 / -0
subnormal numbers
+infinity / -infinity
NaN
```

這份附錄不要求你記住每一種 bit pattern。

現在先抓住核心：

```text
浮點數不是一般整數二進位
而是把 bits 分工表示 sign、scale 與 precision
```

而且 C17 本身也沒有要求所有 `float` / `double` 實作一定使用 IEEE 754 的 binary32 / binary64 格式。IEEE 754 是非常常見且重要的實作模型，但不是這裡要誤寫成唯一語言保證。

---

## 14. `char` 其實也是整數型別

P-U02 會看到：

```c
char grade = 'A';
```

從程式設計的角度，我們把 `grade` 當成字元。

但 C 的 `char` 本質上屬於 integer types。

也就是說，記憶體裡仍然是某個 bit pattern；字元編碼規則告訴我們這個數值要對應哪個字元。

在常見 ASCII 環境中：

```text
'A' → 65 → 01000001
```

所以如果：

```c
char c = 'A';
```

在這類環境上可以從兩個角度看同一份資料：

```text
%c  → 顯示成 A
%d  → 經整數提升後顯示對應數值 65
```

但請注意：

> **C 語言沒有規定 execution character set 一定是 ASCII。**

所以不要把「`'A'` 永遠是 65」當成 C 語言本身的保證。

---

## 15. UTF-8 又多了一層：一個人類字元不一定只佔一個 `char`

ASCII 的英文字母很容易讓人產生：

```text
1 char = 1 個人類看見的字元
```

這個印象。

但處理 UTF-8 時，一個 Unicode 字元可能需要多個 bytes。

所以在一般 UTF-8 環境裡：

```text
'A'
```

通常只需要 1 byte；但像某些中文字元，UTF-8 編碼會使用多個 bytes。

因此 C 的：

```c
char text[]
```

更安全的理解是：

> 它保存一串 `char` 單位；這些單位要透過某個字元編碼規則，才會變成人類看到的文字。

正式課程 F-U04 會再從 C string、`\0`、buffer capacity 的角度處理文字資料。

---

## 16. 位元模式和記憶體中的 byte 順序是兩個問題

假設一個整數需要多個 bytes。

除了「這個值的 binary bit pattern 是什麼」，還會遇到另一個問題：

> 多個 bytes 放進連續記憶體時，哪一個 byte 放在較低位址？

這就是常聽到的 **endianness**。

例如 32-bit 值：

```text
0x12345678
```

在 big-endian 與 little-endian 機器上的 byte 順序可能不同。

這份附錄不深入 endianness，因為它和「二補數怎麼表示負數」是不同層次的問題。

先把它們分開：

```text
representation：一個值用哪些 bits 表示？
endianness：多個 bytes 在記憶體位址中怎麼排列？
```

---

## 17. 回到 P-U02：型別其實在幫我們選解讀規則

現在重新看：

```c
int count = 5;
double temperature = 23.5;
char grade = 'A';
```

表面上只是三個變數用了不同型別。

往下一層看：

```text
int
→ 用整數規則表示與運算

double
→ 用浮點表示與運算規則

char
→ 用整數型別保存一個字元編碼單位，再由字元規則呈現
```

這就是為什麼「型別」不是變數前面的一個裝飾字。

它會影響：

- 哪些值能表示；
- bit pattern 怎麼解讀；
- 哪些運算規則適用；
- 邊界在哪裡；
- 輸入輸出的格式契約。

## 18. 用三個問題確認自己真的看懂

不需要背整份附錄，試著回答：

1. 為什麼同一串 bits 不能脫離型別就直接說「它一定代表什麼」？
2. 在 8-bit two's-complement 模型裡，`00000101` 和 `11111011` 分別怎麼表示 `+5` 與 `-5`？
3. 為什麼 signed integer 的 two's complement 規則不能直接拿來解讀 IEEE 754 的負浮點數？
4. 為什麼 `0.1` 這種十進位小數可能只能近似表示？
5. 為什麼 `char` 的 bit pattern 和「人類看到的字元」中間還需要字元編碼規則？
6. 為什麼不能把 `int = 32 bits`、`ASCII`、`IEEE 754` 都當成 C17 在所有平台上的唯一保證？

如果你能用自己的話回答這些問題，就已經抓到這份附錄真正想建立的模型。
