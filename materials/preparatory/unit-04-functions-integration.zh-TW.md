## 當 `main` 開始做太多事情

上一個 Unit 裡，程式已經會觀察狀態、選擇路徑，也能重複執行工作。這些能力讓我們可以解更有意思的問題，但也帶來一個新的麻煩。

想像現在有一個 `main`，裡面一次做完這些事情：

```text
讀入三次小考成績
→ 拒絕無效輸入
→ 計算平均
→ 判斷及格或再加油
→ 印出報告
```

程式可能還是能正常運作，但所有責任都混在同一個地方。如果及格規則改了，你應該從哪裡找？如果平均算錯了，要檢查多少程式？如果你只想測試「是否及格」這條規則，真的有必要每次都從鍵盤輸入嗎？

這個 Unit 要一路追著一個問題走：

> 程式開始變大之後，怎麼把工作拆成幾個容易命名、理解、測試與修改的部分？

答案就是**函數**。

讀完本 Unit 後，你應該能閱讀與撰寫小型函數，說明參數與引數的關係，追蹤回傳值如何回到呼叫者，將一個需求拆成幾個責任，並在函數介面改變時找到需要一起更新的呼叫與測試。

本 Unit 的活動不需繳交。接近結尾時有一個完全選做的 AI 延伸；直接跳過不影響本 Unit。

---

## 1. 先從一件容易命名的工作開始

假設程式很多地方都需要找出兩個整數中較大的那一個。

你當然可以每次都重寫同一段 `if`，但這項工作其實已經很好命名：

> 接收兩個整數，回傳其中較大的值。

它可以變成一個函數：

```c
int max_of_two(int a, int b) {
    if (a > b) {
        return a;
    }

    return b;
}
```

先把第一行從左到右讀一次：

```c
int max_of_two(int a, int b)
```

- 第一個 `int` 表示這個函數會回傳一個整數結果。
- `max_of_two` 是函數名稱。
- `a` 與 `b` 是函數工作時接收到的值。

函數本體只回答一個問題：哪一個比較大？

它不讀鍵盤、不印報告，也不決定整支程式接下來要做什麼。

正因為責任很單純，這個函數才容易理解，也容易重複使用。

---

## 2. 呼叫函數，接住它的結果

函數只被定義出來並不會自己執行。程式的另一個地方必須**呼叫**它。

```c
#include <stdio.h>

int max_of_two(int a, int b) {
    if (a > b) {
        return a;
    }

    return b;
}

int main(void) {
    int larger = max_of_two(5, 8);
    printf("%d\n", larger);
    return 0;
}
```

預期輸出：

```text
8
```

這一段就是函數呼叫：

```c
max_of_two(5, 8)
```

其中 `5` 與 `8` 是**引數**：呼叫者實際送進去的值。

進入函數之後，這些值分別由**參數** `a` 與 `b` 接收。

對這一次呼叫來說，可以把關係想成：

```text
呼叫者送出 5 和 8
        ↓
a 變成 5，b 變成 8
        ↓
函數比較兩者
        ↓
return 8
        ↓
呼叫者把 8 存進 larger
```

參數屬於函數的定義；引數則屬於某一次實際的呼叫。

---

## 3. 先把一次呼叫追完，再加更多函數

再走一次這一行：

```c
int larger = max_of_two(5, 8);
```

| 步驟 | 執行位置 | 發生什麼事？ |
|---|---|---|
| 1 | `main` | 準備引數 `5` 與 `8` |
| 2 | `max_of_two` | 以 `a = 5`、`b = 8` 接收它們 |
| 3 | `max_of_two` | 判斷 `a > b`，結果為 false |
| 4 | `max_of_two` | 執行 `return b;`，產生 `8` |
| 5 | `main` | 把回傳的 `8` 存進 `larger` |

函數正在執行時，呼叫者正在等待這次呼叫完成。遇到 `return` 之後，執行流程回到原本使用這個函數的位置。

先記住最基本的圖像就好：

```text
引數送進去
→ 函數完成一項責任
→ 回傳值送回來
```

---

## 4. 好的函數名稱應該說得出它負責什麼

看看下面兩個想法：

```c
int calculate_average_of_three(int a, int b, int c);
int is_passing(double average, double threshold);
```

光看名稱，大致就能知道每一部分在做什麼。

第一個負責計算平均；第二個負責回答「有沒有及格」這個判斷問題。

這樣一來，程式其他地方可以負責協調整體流程，不必同時塞進所有計算與規則。

一個很實用的檢查方式，是試著把這句話補完：

> 這個函數負責 ________。

如果空格裡需要塞進一長串用「而且」連起來的工作，這個函數可能做太多事了。

例如：

```text
讀輸入，而且算平均，而且判斷，而且印報告
```

通常就比幾個各自負責一件事的函數更難理解。

目標不是函數越多越好，而是重要責任都能很快找到，也能清楚說明。

---

## 5. 讓函數的介面說清楚

當呼叫者知道哪些值可以傳入、會得到什麼結果時，函數會更容易安全使用。

假設我們定義：

```c
int add_bonus(int score, int bonus) {
    return score + bonus;
}
```

在這個前導範例裡，我們先讓需求明確規定：

```text
score 必須介於 0 到 100
bonus 必須介於 0 到 20
```

因為輸入範圍被刻意限制住，最大結果只會是 120，所以在符合 C 標準的實作中，這個加法一定落在一般 `int` 可表示的範圍內。

這些條件就是函數**介面契約**的一部分：

```text
輸入：score 0..100、bonus 0..20
結果：score + bonus
責任：只負責計算
```

函數本身不必讀鍵盤，也不必顯示任何東西。

呼叫者可以先確認需求，再進行呼叫：

```c
if (score < 0 || score > 100 || bonus < 0 || bonus > 20) {
    printf("Invalid input\n");
    return 1;
}

int adjusted = add_bonus(score, bonus);
```

這裡先建立一個很重要的設計習慣：

> 要知道函數承諾什麼，也要知道呼叫之前，呼叫者必須先保證什麼。

到了正式課程，我們會再處理更複雜的介面，例如用指標帶回輸出、檢查整數範圍，以及失敗時如何保留原本狀態。那些都很重要，但目前不需要先懂它們，才能理解函數最基本的概念。

---

## 6. 函數定義放在 `main` 後面時，先宣告它

目前為止，我們都把函數定義放在 `main` 前面，所以編譯器在看到呼叫之前，已經看過完整函數。

你也可以把定義放在檔案後面。這時就先用宣告告訴編譯器函數介面；這種宣告通常稱為**函數原型**：

```c
#include <stdio.h>

int max_of_two(int a, int b);

int main(void) {
    printf("%d\n", max_of_two(5, 8));
    return 0;
}

int max_of_two(int a, int b) {
    if (a > b) {
        return a;
    }

    return b;
}
```

現在可以把三個相關概念分開：

- **宣告／原型**：告訴編譯器函數介面。
- **定義**：包含函數本體與實際工作。
- **呼叫**：用特定引數請函數執行。

宣告與定義的回傳型別、參數型別必須一致。

## 7. 用幾個責任組成成績報告器

回到本 Unit 開頭那支逐漸變大的程式。

需求是：

> 讀入三次 0 到 100 的小考成績，計算平均；如果平均至少達到指定門檻就印出 `Pass`，否則印出 `Try again`。

不要把計算與判斷全部直接寫在 `main` 裡，先幫這兩項工作命名：

```c
double average_of_three(int a, int b, int c) {
    return (a + b + c) / 3.0;
}

int is_passing(double average, double threshold) {
    return average >= threshold;
}
```

因為每一個小考成績都已先確認介於 0 到 100，所以 `a + b + c` 最大只有 300；這個範例不會因此產生整數溢位問題。

完整的小程式可以變成：

```c
#include <stdio.h>

double average_of_three(int a, int b, int c) {
    return (a + b + c) / 3.0;
}

int is_passing(double average, double threshold) {
    return average >= threshold;
}

int main(void) {
    int q1;
    int q2;
    int q3;
    const double threshold = 60.0;

    if (scanf("%d %d %d", &q1, &q2, &q3) != 3) {
        printf("Invalid input\n");
        return 1;
    }

    if (q1 < 0 || q1 > 100 ||
        q2 < 0 || q2 > 100 ||
        q3 < 0 || q3 > 100) {
        printf("Invalid input\n");
        return 1;
    }

    double average = average_of_three(q1, q2, q3);

    printf("Average: %.1f\n", average);

    if (is_passing(average, threshold)) {
        printf("Pass\n");
    } else {
        printf("Try again\n");
    }

    return 0;
}
```

`scanf` 裡的 `&` 就是前面輸入範例曾經看過的位址語法。指標概念會在正式課程完整建立；這個 Unit 現在真正要觀察的是「輸入成功之後，責任怎麼被拆開」。

現在把 `main` 當成故事讀一次：

```text
讀取
→ 驗證
→ 計算平均
→ 顯示平均
→ 判斷是否及格
```

細部計算與判斷都有自己的名稱，所以可以分別查看與測試。

---

## 8. 不用每次都跑完整程式，也可以測一個函數

因為 `average_of_three` 不自己讀輸入，也不自己印輸出，所以我們可以直接針對它推理。

| 呼叫 | 預期結果 |
|---|---:|
| `average_of_three(60, 60, 60)` | 60.0 |
| `average_of_three(59, 60, 61)` | 60.0 |
| `average_of_three(100, 100, 100)` | 100.0 |
| `average_of_three(0, 0, 0)` | 0.0 |

判斷函數也可以單獨確認：

| 呼叫 | 預期意義 |
|---|---|
| `is_passing(59.9, 60.0)` | false／0 |
| `is_passing(60.0, 60.0)` | true／非 0 |
| `is_passing(60.1, 60.0)` | true／非 0 |

這就是分離責任很重要的原因之一：結果不對時，我們可以把問題縮小。

不要只問：

> 為什麼整支程式錯了？

可以改問：

> 是輸入失敗？平均計算錯？還是及格判斷錯？

---

## 9. 三種常見的函數錯誤

### 9.1 算出了回傳值，卻沒有使用

這個呼叫會算出一個值，然後立刻把它丟掉：

```c
average_of_three(80, 70, 90);
```

如果後面還要使用結果，就應該把它存起來或直接拿去使用：

```c
double average = average_of_three(80, 70, 90);
```

### 9.2 一個函數塞進太多責任

像下面這種函數，會用一個模糊的名稱包住好幾種不同工作：

```c
void do_everything(void) {
    /* read, validate, calculate, decide, print */
}
```

只要其中一條規則改變，就很難快速判斷應該改哪一段、測哪一段。

### 9.3 引數順序放反

假設介面是：

```c
int subtract(int left, int right);
```

那麼：

```c
subtract(10, 2)
```

和：

```c
subtract(2, 10)
```

就是兩次不同的呼叫。參數順序也是介面的一部分。

名稱可以幫忙理解，但呼叫者仍然要知道每一個位置代表什麼。

---

## 10. 需求改變時，沿著介面找影響範圍

假設第一版函數固定加 5 分：

```c
int add_bonus(int score) {
    return score + 5;
}
```

之後需求改成：

> 加幾分要由呼叫者決定。

新的介面比較適合寫成：

```c
int add_bonus(int score, int bonus) {
    return score + bonus;
}
```

這次修改不只影響函數本體。

還要一起找：

1. 函數宣告，如果有的話。
2. 每一個呼叫位置。
3. 新的 `bonus` 引數允許哪些範圍。
4. 不同 bonus 值需要哪些測試。
5. 原本應該繼續成立的行為，例如 bonus 仍然是 5。

例如舊呼叫：

```c
add_bonus(score)
```

現在就要改成類似：

```c
add_bonus(score, 5)
```

函數介面是程式不同部分之間的連接。只改其中一邊、沒有更新另一邊，這個連接就會斷掉。

## 11. 試著自己寫並追蹤 `max_of_two`

自己完成這個函數：

```c
int max_of_two(int a, int b);
```

實作前先選四組測試：

| `a` | `b` | 預期結果 |
|---:|---:|---:|
| 5 | 3 | 5 |
| 2 | 7 | 7 |
| 4 | 4 | 4 |
| -2 | -5 | -2 |

接著選一組呼叫，從引數開始，經過條件判斷，一路追到回傳值。

如果其中一列失敗，不要立刻把整個函數重寫。先找出哪一個判斷最早和你原本預期的追蹤不一樣。

## 12. 再試一次：完成成績報告器

建立一支小程式：

1. 讀入三個整數小考成績。
2. 拒絕非數字輸入，以及不在 0 到 100 的成績。
3. 用一個函數計算平均。
4. 用另一個函數判斷 `Pass` 或 `Try again`。
5. 印出結果。

可以先準備這些測試：

```text
59 60 61 → average 60.0 → Pass
60 60 59 → average 59.7 → Try again
100 100 100 → average 100.0 → Pass
0 0 0 → average 0.0 → Try again
101 80 80 → Invalid input
非數字輸入 → Invalid input
```

不要一開始就把全部程式碼一次寫完。先決定責任與預期結果，再實作第一個函數、測試它，接著加入下一部分。

## 13. 選做：用 AI 挑戰自己的函數解釋

如果想多做一個練習，先不用任何工具，用自己的話回答：

> 參數和引數有什麼不同？把一段計算拆成函數，為什麼會讓測試與需求修改更容易？

之後可以把自己的解釋交給 AI，請它挑出不清楚的地方或提出不同說法。這完全是選做活動，不需要固定 Prompt，也不需要保存對話。

如果 AI 的說法和函數追蹤、編譯結果、直接測試或已寫清楚的介面不一致，就回到這些證據重新判斷。

## 14. 往下一階段以前，試著不要背定義，而是解釋

請從本 Unit 的其中一支程式出發回答：

- 每一個函數各自負責什麼？
- 哪些值是參數？哪些是引數？
- `return` 執行後，回傳值去了哪裡？
- 為什麼 `average_of_three` 不同時負責讀輸入與印輸出時，更容易測試？
- 函數介面多了一個參數之後，哪些地方需要一起修改？
- 為什麼有效輸入範圍也是理解介面的一部分？

如果答案太抽象，就選一個具體呼叫：

```c
max_of_two(5, 8)
```

把每個值一步一步追完。

## 15. 本章收尾

前導課程從一個文字檔如何變成真正執行中的程式開始。接著，程式有了值與狀態，學會選擇不同路徑與重複工作，最後再用函數把逐漸變大的工作拆成有名稱的責任。

函數讓大型程式開始有結構。引數把值送進一次呼叫，參數接住這些值，而回傳值再把結果帶回呼叫者。責任清楚之後，我們比較容易解釋程式、單獨測試某一部分，也比較知道需求改變時該修改哪些地方。

到這裡，前導課程的主線就走完了。正式課程會先回頭深挖一件看起來已經很熟悉的事：值與型別。我們已經多次使用 `int`、`double`、算術與輸入，但它們背後其實還藏著表示方式、轉換規則與邊界行為；程式越大，這些細節越不能只靠直覺。

所以下一個問題是：為什麼程式碼看起來合理時，表示方式、型別與運算仍然可能讓結果改變？
