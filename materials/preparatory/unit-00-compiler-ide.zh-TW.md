# 前導單元 P-U00：寫好的 C 程式，怎麼真的跑起來？

版本：1.3.0  
狀態：學生教材  
最後更新：2026-08-10  
對應英文版本：[Preparatory Unit P-U00: How Does the C Code You Write Actually Start Running?](unit-00-compiler-ide.en.md)

在開始碰 C 語法或開發工具以前，先把這門課正在做的事情放回一個比較大的畫面。

假設有人說：

> 幫我判斷一個學生成績是不是及格；60 分以上顯示 `Pass`，否則顯示 `Try again`。

就算現在還不會 C，你其實已經可以開始想：

```text
資料：一個成績
規則：成績是否 >= 60
結果：Pass 或 Try again
```

這時我們還沒有寫任何 C 程式碼，但已經在做程式設計最重要的一部分：把問題整理成電腦可以一步一步處理的資料、規則與結果。

---

## 0. 程式、程式語言、程式設計分別是什麼？

這三個詞很常一起出現，但它們不是同一件事。

### 程式（program）

可以先把程式理解成：**交給電腦執行的一套明確工作描述。**

它可能接收資料、按照規則處理，再產生可以觀察的結果。例如：

```text
讀入成績
→ 判斷是否達到 60
→ 顯示 Pass 或 Try again
```

程式不一定要很大。只要它描述了一套可以被執行的工作，就已經是一個程式問題。

### 程式語言（programming language）

我們可以用自然語言說：

```text
如果成績至少 60，就顯示 Pass。
```

也可以先把它寫得更結構化：

```text
if score >= 60
    print Pass
else
    print Try again
```

而在這門課使用的 C 裡，之後會看到類似：

```c
if (score >= 60) {
    printf("Pass\n");
} else {
    printf("Try again\n");
}
```

現在完全不需要看懂這段 C 語法。先觀察一件事就好：**同一個問題，可以用一套更精確、讓工具能處理的規則來表達。**

程式語言就是這樣的一套表達系統。這門課選擇用 C 來練習。

### 程式設計（programming）

程式設計不只是「把 C 語法打進電腦」。比較完整的過程是：

```text
理解問題
→ 決定需要哪些資料
→ 想出處理規則
→ 用程式語言表達
→ 讓程式執行
→ 觀察結果
→ 和需求比較
→ 必要時修改
```

所以寫 code 是程式設計的一部分，但不是全部。後面每個 Unit 反覆出現的 prediction、trace、test、debug 與 requirement change，都是這個過程的一部分。

接下來我們會把剛才的想法寫成 C。寫下來之後，首先得到的是 **source code（原始碼）**，也就是程式的文字表示。新的問題也就出現了：

> 這些文字怎麼真的變成電腦正在執行的程式？

你在課堂上很可能會使用一套叫做 **IDE（Integrated Development Environment，整合式開發環境）** 的工具。它把編輯程式、Build、Run、Debug 等工作放在同一個操作環境裡。現在先知道它是「協助我們完成開發工作的整合環境」就夠了；等我們把 source、Build、executable 與 Run 分開看過，再回來拆 IDE 裡每個角色會更清楚。

這個 Unit 真正要建立的是下面這條之後會一直使用的路徑：

```text
你寫的 C 原始碼
→ 編譯與建置工具處理原始碼
→ 產生可以執行的程式
→ 作業系統啟動它
→ 程式執行並產生可觀察結果
```

### 你可以從三個不同入口理解同一條路

每個人第一次對開發工具「有感」的位置不一定一樣。這一章會把三種常見入口接到同一個模型：

- **如果你比較熟 IDE**：先從「我按下 Run 時，IDE 替我做了哪些工作？」來看。
- **如果你比較喜歡看得見的檔案與指令**：先從 `hello.c`、Build 指令和產生的 executable 來看。
- **如果你通常是遇到問題才開始理解工具**：先記住後面的「原始碼改了，結果卻還是舊的」實驗，再回頭找是哪一個步驟沒有更新。

三種入口最後都會回到同一件事：**source、Build、executable、Run 是不同角色；IDE 把它們整合起來，但沒有把它們變成同一件事。**

如果其中一種說法暫時沒有感覺，可以先沿著另一種往下讀；後面的例子會反覆從不同角度碰到同一個流程。

---

## 1. 先從一個普通文字檔開始

建立一個檔案，名稱叫做：

```text
hello.c
```

內容是：

```c
#include <stdio.h>

int main(void) {
    printf("Hello, C!\n");
    return 0;
}
```

如果你平常習慣寫完就按 Run，這次可以先停一下，只看目前手上的東西。

這個 `hello.c` 此刻是一份 **source file（原始檔）**。裡面的內容是 **source code（原始碼）**。

你可以打開它、閱讀它、修改它，但光是儲存這份文字，不代表電腦已經開始執行裡面的 C 程式。

這是第一個要分清楚的事情：

```text
我把程式碼寫進檔案
```

和

```text
電腦正在執行這支程式
```

不是同一件事。

---

## 2. Compiler 做的是什麼？

C 原始碼是寫給人類與 C 工具理解的文字。要真正執行，必須先經過編譯與建置工具處理。

如果你的環境使用 GCC，可以在終端機輸入：

```text
gcc hello.c -o hello
```

不同作業系統、compiler 或課堂環境的指令可能不同；如果老師指定其他指令，就使用老師提供的版本。現在重要的不是背 `gcc`，而是觀察這個動作的角色。

在這個只有一個 `.c` 檔的小例子裡，這條指令會替我們完成建立可執行結果所需的工作。成功之後，目錄裡會出現一個可以執行的結果；在不同系統上，它可能叫做 `hello`、`hello.exe`，或由開發環境放在某個 build 目錄中。

現在先把最重要的關係想成：

```text
hello.c
  │
  │ compiler / build tools
  ▼
executable
```

如果原始碼不符合工具能接受的 C 規則，例如少了一個分號，這次 Build 就可能失敗，也就不會得到對應的新 executable。

後面程式變成多個檔案時，Build 還會有更細的步驟；現在先不用一次學完。

---

## 3. Compile／Build 和 Run 是兩件不同的事

現在才執行剛剛產生的程式。

在某些終端機環境中可能是：

```text
./hello
```

在 Windows 環境中則可能執行：

```text
hello.exe
```

你會看到：

```text
Hello, C!
```

剛才其實做了兩類不同的事情：

```text
Build
hello.c → executable

Run
executable → running program → output
```

所以：

- Build／compile-related work 是讓目前的原始碼形成最新可執行結果。
- Run 是啟動已經存在的 executable。

之後看到 Build、Run、Debug 等按鈕時，可以試著問：**現在到底正在做哪一個階段？** 這個問題通常比只記按鈕名稱更能幫你換到另一套 IDE。

---

## 4. 一個很重要的小實驗：改了原始碼，但先不要重新 Build

把原始碼改成：

```c
#include <stdio.h>

int main(void) {
    printf("Goodbye, C!\n");
    return 0;
}
```

儲存 `hello.c`。

現在先不要重新 Build，直接執行剛才那個 executable。

先預測會看到：

```text
Hello, C!
```

還是：

```text
Goodbye, C!
```

如果你執行的仍然是上一輪 Build 產生的 executable，就會看到舊的結果：

```text
Hello, C!
```

原因不是電腦「沒有看到你存檔」，而是：

```text
你改的是 hello.c
但你執行的是先前產生的 executable
```

兩者不是同一個檔案。

現在重新 Build，再執行一次，才會看到：

```text
Goodbye, C!
```

這個實驗之後會非常有用。當你遇到「明明改了程式，結果怎麼沒變」時，可以先問：

> 我真的重新 Build 了嗎？我現在執行的是最新產生的 executable 嗎？

如果前面的流程圖比較抽象，這個實驗可以反過來幫你理解它：**source 改變的是文字；Build 才把新的文字變成新的 executable；Run 執行的是 executable。**

---

## 5. 現在回頭看：IDE 到底是什麼？

前面先把 IDE 簡單理解成「整合開發工作的環境」。現在 source、Build 與 Run 已經分開了，可以把它正式拆開。

IDE 是 **Integrated Development Environment（整合式開發環境）**。

它通常把很多開發時常用的功能放在同一個介面裡，例如：

```text
IDE
├─ editor：編輯原始碼
├─ build integration：呼叫 compiler 與相關工具
├─ run：啟動程式
├─ terminal：直接輸入指令
└─ debugger：暫停並觀察程式執行
```

不同 IDE 的畫面與按鈕位置會不同，但這些角色比按鈕長什麼樣子更重要。

如果你原本把 IDE 和 compiler 想成同一個東西，可以把模型稍微拆開：

```text
IDE ≠ compiler
```

比較準確的理解是：

> IDE 幫你把編輯、建置、執行、除錯與其他開發工作整合在一起；真正處理 C 原始碼的是 compiler 與相關建置工具。

這也是為什麼有些編輯器可以打開 `.c` 檔，卻不代表電腦已經具備可用的 C 開發工具。

你也可以從另一個角度想：**IDE 是操作介面；compiler、debugger 等是被它整合或呼叫的工具。** 換一套 IDE 時，介面可能整個變了，但底下這些工作角色仍然存在。

---

## 6. Build 和 Compile 為什麼有時看起來不完全一樣？

在只有一個很小的 `hello.c` 時，可以先把 Build 理解成「讓目前的原始碼變成最新可執行結果所需要的工作」。

對非常小的程式來說，你看到的主要工作就是編譯相關處理。

但是以後程式變大、拆成多個檔案之後，一次 Build 可能包含不只單一編譯動作。正式課程後面的模組化 Unit 會再把 compile 與 link 拆開來看。

目前保留這個模型就夠用了：

```text
Edit source
→ Build
→ 得到最新可執行結果
→ Run
```

後面的建置細節等真的需要多檔案時再拆開，通常會比現在一次記住更有意義。

---

## 7. Run 和 Debug 也不是同一件事

Run 的目標通常是直接執行程式。

Debug 模式則讓你有機會在程式執行途中停下來觀察。

先不用變數，只看兩行輸出：

```c
printf("First\n");
printf("Second\n");
```

如果在第二行設下 **breakpoint（中斷點）**，debugger 可以讓程式執行到第二行以前先暫停。這時你可以觀察到：第一行已經產生輸出，而第二行還沒有執行。

這已經足以看出 Debug 和一般 Run 的差別：

```text
Run：讓程式直接往前執行
Debug：讓程式可以在途中暫停、逐步前進、觀察當下發生了什麼
```

現在不需要學會所有 debugger 功能。等我們後面開始學資料與狀態，再去觀察變數會更有意義；正式課程也會把 debugger 放進完整的測試與除錯流程中。

如果你比較喜歡把概念想成「影片」，可以把 Run 想成直接播放；Debug 則像在播放途中按暫停、逐格往前，觀察目前走到哪裡。這個比喻只用來理解控制執行節奏，不代表 debugger 真的在播放預先錄好的影片。

---

## 8. Build 成功和程式正確是不同問題

看這支程式：

```c
#include <stdio.h>

int main(void) {
    printf("Goodbye, C!\n");
    return 0;
}
```

它可能成功 Build，也能成功 Run。

但如果需求是：

```text
輸出 Hello, C!
```

它仍然做錯了事情。

因此之後我們會一直區分：

```text
工具有沒有接受並成功建立程式？
↓
程式有沒有真的被啟動並執行？
↓
實際結果有沒有符合需求？
```

這三題不能互相取代。

換一個角度看，Build 像是在回答「這份程式能不能形成可執行結果？」；需求測試回答的則是「形成的結果是不是我們真正想要的？」兩者都重要，但回答的是不同問題。

---

## 9. 走一次完整流程

建立：

```text
intro.c
```

讓它輸出兩行：

```text
My name is <你的英文名字>.
I am learning C.
```

這次除了把程式跑出來，也試著在每一步說出自己正在做什麼：

1. 我正在編輯哪一個 source file？
2. 我什麼時候儲存了它？
3. 我什麼時候 Build？
4. Build 成功後產生或更新了什麼？
5. 我真正 Run 的是哪一個程式？
6. Output 是否符合我原本預期？

如果使用 IDE，可以找出 editor、terminal、Build、Run、Debug 分別在哪裡；如果使用終端機，就把你輸入的指令對回同一條流程。兩種操作方式是在看同一個模型。

---

## 10. 用實際操作檢查自己的理解

試著不用教材原句，直接從剛才的 `hello.c` 回答：

- 程式、程式語言、程式設計三者有什麼不同？
- `hello.c` 和 executable 是同一個檔案嗎？
- 修改 `hello.c` 後，為什麼舊 executable 不會自動改變？
- Build 和 Run 各自在做什麼？
- IDE 和 compiler 為什麼不能直接畫上等號？
- Build 成功為什麼不能證明結果符合需求？
- Run 和 Debug 的目的有什麼不同？
- 如果你改了原始碼，但執行結果仍然是舊的，第一批應該檢查什麼？

有些人用流程圖比較容易想清楚，有些人要真的跑過一次舊 executable 才會有感。只要你最後能把自己的操作對回「問題 → 程式語言表達 → source → Build → executable → Run → 觀察結果」，就代表這個模型開始站穩了。

---

## 11. 接下來：開始讀真正執行中的程式

現在我們已經從「想解決一個問題」一路走到真正執行程式：先用 C 把解法寫成 source code，再經過 Build 形成 executable，最後由 Run 啟動它；IDE 則把這些開發工作整合在一起。

下一個 Unit 不再把重點放在工具，而會開始追蹤：**當程式真的執行時，`main` 裡的敘述怎麼一步一步變成我們看到的結果？**
