# 正式單元 F-U01：表示、型別與運算為什麼會影響結果？

版本：1.1.0  
狀態：正式學生教材  
最後更新：2026-08-09  
對應英文版本：[Formal Unit F-U01: Why Do Representation, Type, and Operations Affect Results?](unit-01-representation-types.en.md)

前導課程裡，我們已經用了很多次 `int`、`double`、算術與輸入。當時最重要的是先讓程式的資料流、控制流程與函數責任變得清楚。

現在先看一段看起來很普通的程式：

```c
int a = 5;
int b = 2;
double result = a / b;

printf("%.1f\n", result);
```

如果你預期看到 `2.5`，實際結果會讓你停一下：

```text
2.0
```

問題不在 `double result`。真正決定除法規則的是運算發生當下的兩個運算元：`a` 和 `b` 都是 `int`，所以 `a / b` 先完成整數除法，得到 `2`；之後再把這個結果轉成 `double`，已經不可能把被捨去的小數補回來。

這個例子揭開正式課程的第一個主題：**程式中的值不只「是多少」而已；它怎麼表示、被當成什麼型別，以及在哪個時間點進行什麼運算，都會影響結果。**

這個 Unit 會沿著這個問題往下走。

---

## 1. 一串位元本身還沒有完整故事

先看這八個位元：

```text
10110010
```

如果只看到這串 `0` 與 `1`，你還不能完整回答「它代表什麼」。它可能被某個程式當成無號整數的一部分、有號整數的表示、字元資料的一部分，或其他格式中的欄位。

可以先把三個容易混在一起的概念拆開：

- **值（value）**：我們想討論的抽象結果，例如十進位的 45。
- **表示（representation）**：這個值在某種規則下如何用位元保存。
- **型別（type）**：程式用什麼規則解讀這些資料，以及允許哪些運算。

例如，十進位的 45 可以寫成無號二進位：

```text
00101101
```

這裡的位元沒有自己附帶「我是 45」的標籤。是我們先指定「把它當成無號二進位整數」，才得到這個解讀。

所以遇到一串位元時，不要急著只問：

> 它是多少？

更好的問題是：

> 我現在用什麼表示規則與型別來解讀它？

---

## 2. 從 LSB 往左看權重

對固定位數的無號二進位整數，可以先從最右邊開始：

```text
0 0 1 0 1 1 0 1
^             ^
MSB           LSB
```

- **LSB（Least Significant Bit）** 是最右側、權重最低的位元。
- **MSB（Most Significant Bit）** 是最左側、權重最高的位元。

對無號二進位整數而言，從 LSB 開始的權重依序是：

```text
128 64 32 16 8 4 2 1
 0  0  1  0 1 1 0 1
```

因此：

```text
00101101
= 32 + 8 + 4 + 1
= 45
```

這裡有一個值得先記住的細節：**MSB 是位置名稱，不等於「永遠都是正負號位元」。**不同資料表示法會給最高位元不同的角色。這個 Unit 先用無號整數建立位置與權重的直覺，不需要先把所有有號整數表示法背起來。

---

## 3. 型別不只是變數前面的關鍵字

看看這幾個宣告：

```c
unsigned int count = 10;
int change = -3;
double ratio = 0.5;
char letter = 'A';
```

表面上只是變數前面的型別名稱不同，但型別其實會影響很多事情：

- 哪些值可以被表示。
- 某個運算應採用什麼規則。
- 不同型別一起運算時要如何轉換。
- `printf` 與 `scanf` 應使用哪一種格式。
- 某些邊界之外的運算是否仍有定義。

而且不要把 `int` 想成「永遠固定幾個位元、永遠固定某個最大值」。C 對許多整數型別規定的是最低能力與相對關係，實際範圍應由實作環境與標準標頭提供。

例如：

```c
#include <limits.h>
#include <stdio.h>

int main(void) {
    printf("INT_MIN = %d\n", INT_MIN);
    printf("INT_MAX = %d\n", INT_MAX);
    return 0;
}
```

這比在程式裡憑印象寫死某個 `int` 最大值可靠得多。

---

## 4. 回到開頭：運算先發生，儲存才發生

現在重新看開頭的例子：

```c
int a = 5;
int b = 2;

double x = a / b;
double y = (double)a / b;
```

先不要執行，自己預測：

```text
x = ?
y = ?
```

答案是：

```text
x = 2.0
y = 2.5
```

兩行的差別在運算之前。

第一行：

```c
a / b
```

兩個運算元都是 `int`，所以先做整數除法，得到 `2`；接著才把 `2` 轉成 `double` 存進 `x`。

第二行：

```c
(double)a / b
```

`a` 在除法發生前先轉成 `double`。因此這次除法會以浮點規則進行，得到 `2.5`。

可以把它讀成兩條不同的資料流：

```text
5(int) / 2(int) → 2(int) → 2.0(double)
```

以及：

```text
5(int) → 5.0(double)
5.0(double) / 2(int) → 2.5(double)
```

當結果和直覺不同時，先問「運算發生時，運算元是什麼型別？」通常比只看左邊的儲存變數更有用。

---

## 5. 格式字串也是型別契約

型別不只影響算術，也影響輸出與輸入。

例如：

```c
int n = 42;
double x = 3.14;

printf("%d\n", n);
printf("%f\n", x);
```

`%d` 告訴 `printf`：「下一個對應引數要按照 `int` 的規則取得。」

`%f` 在 `printf` 裡則要求對應的引數是 `double`。

如果寫成：

```c
printf("%d\n", 3.14);
```

這不是單純「畫面印得不好看」。`%d` 要求的是 `int`，實際傳入的是 `double`，兩邊的型別契約不一致；對 `printf` 這類可變參數函數（variadic function）而言，這會造成**未定義行為（undefined behavior）**。

因此遇到格式警告時，不要把它當成美觀問題。像下面這樣開啟警告：

```text
-Wall -Wextra -Wformat=2 -pedantic
```

編譯器通常可以在你執行程式以前就指出這類型別不匹配。

這也是為什麼「能編譯」和「程式行為有正確定義」不是同一件事。

---

## 6. 同一個 `char` 可以用不同方式呈現

再看一個比較直觀的例子：

```c
char c = 'A';

printf("%c\n", c);
printf("%d\n", c);
```

第一行要求把值呈現成字元，第二行則以整數形式顯示轉換後的數值。

這提醒我們：**資料本身與顯示方式不是同一件事。**格式字串決定 `printf` 要如何解讀對應引數並把它呈現出來。

但是不要因此直接背：

> `'A'` 一定等於 65。

在常見 ASCII 環境中確實如此，但 C 語言本身沒有要求 execution character set 一定是 ASCII。除非你的環境或題目規格明確指定，否則不要把特定字元碼當成語言保證。

---

## 7. `0.1 + 0.2` 為什麼值得拿來看？

整數的問題常出現在邊界與運算規則；浮點數則還多了一件事：**許多我們熟悉的十進位小數，不能用有限長度的二進位浮點表示精確保存。**

試試：

```c
#include <stdio.h>

int main(void) {
    double x = 0.1 + 0.2;
    printf("%.17f\n", x);
    return 0;
}
```

你可能看到一個非常接近 `0.3`、但最後幾位不同的結果。

這不代表電腦「算錯加法」，而是 `0.1`、`0.2` 這些十進位值在二進位浮點系統中通常只能保存成鄰近的可表示值，後續運算也在這些近似值上進行。

所以對「計算得到的近似數值」直接寫：

```c
if (x == 0.3) {
    /* ... */
}
```

往往不是你真正想要的判斷。

一種常見做法是使用容許誤差：

```c
#include <math.h>

if (fabs(x - 0.3) < 1e-9) {
    printf("close enough\n");
}
```

但 `1e-9` 不是魔法常數。合理的門檻要由需求、數值尺度與你能接受的誤差決定。

也不要把這件事誤解成「浮點數永遠不能用 `==`」。如果你比較的是刻意設計的精確哨兵值，例如檢查使用者是否直接輸入 `0.0` 來表示「零除數」，精確比較可能正是規格要表達的意思。關鍵仍然是：**你的比較規則要符合資料是怎麼產生的，以及需求真正想判斷什麼。**

---

## 8. 邊界附近，直覺最容易失效

先不要猜 `int` 最大值，讓標頭告訴你：

```c
#include <limits.h>
#include <stdio.h>

int main(void) {
    printf("%d\n", INT_MAX);
    return 0;
}
```

接著想像：

```c
int x = INT_MAX;
int y = x + 1;
```

對有號整數而言，超出可表示範圍的算術溢位是**未定義行為**。你不能因為某一次執行剛好看到它「回到負數」，就把那個結果當成 C 語言保證。

如果需求允許 `x + y`，而輸入又可能接近邊界，就應在真正相加之前先確認運算是否安全。例如當 `y > 0` 時，可以先判斷：

```c
if (x > INT_MAX - y) {
    printf("would overflow\n");
} else {
    int sum = x + y;
    printf("%d\n", sum);
}
```

這裡的重要順序是：**先檢查，後運算。**如果先做出已溢位的結果，再檢查結果是否奇怪，就已經太晚了。

無號整數不同。無號算術依模數規則運作，所以超過最大值後會依規則回繞。這是有定義的行為，但「有定義」不代表「符合需求」。只有當你的問題真的需要 modular arithmetic 時，回繞才可能是正確答案。

---

## 9. 不要把所有「怪結果」都叫做同一種錯

現在我們已經遇到幾種看起來都像「結果不對」的情況，但它們其實不同：

| 情況 | C 的行為有沒有定義？ | 真正要問的問題 |
|---|---|---|
| `5 / 2` 得到 `2` | 有 | 這是不是需求想要的除法規則？ |
| 計算後的浮點值直接用 `==` 比較 | 有 | 比較方式是否符合近似資料的需求？ |
| 有號整數超出可表示範圍 | 沒有 | 能不能在運算前阻止溢位？ |
| `printf("%d", 3.14)` | 沒有 | 格式與實際引數型別是否一致？ |

這個分類很重要。

「有定義但不符合需求」通常是邏輯或需求層的問題；「未定義行為」則表示語言不再保證你能從一次觀察推導出可靠結果。

所以除錯時，不要只問：

> 為什麼輸出不是我想的？

可以再往前一步：

> 我現在遇到的是合法但不符合需求的規則，還是已經踏進未定義行為？

---

## 10. 做三個小實驗，把規則變成可觀察的證據

### 實驗 A：整數除法與轉型時機

預測並執行：

```c
printf("%d\n", 7 / 3);
printf("%.6f\n", 7.0 / 3);
printf("%.6f\n", (double)7 / 3);
```

不要只記答案。試著逐行說出「除法發生時兩邊是什麼型別」。

### 實驗 B：同一個無號整數的十進位與十六進位

```c
unsigned int value = 45;
printf("%u %x\n", value, value);
```

兩個輸出看起來不同，但它們不是兩個不同的 `value`。只是同一個數值用了不同的文字表示方式。

### 實驗 C：只編譯格式不匹配，不執行

建立這段程式：

```c
#include <stdio.h>

int main(void) {
    printf("%d\n", 3.14);
    return 0;
}
```

用：

```text
-Wall -Wextra -Wformat=2 -pedantic
```

編譯並閱讀警告。這個實驗的目的不是「看看未定義行為今天印出什麼」，而是練習在執行以前就用靜態診斷找到契約不匹配。

## 11. 自主練習：做一個表示與除法報告器

建立一支小程式，讀入：

```text
一個 unsigned int 數值
一個 double 除數
```

輸入成功後，程式要顯示：

1. 整數的十進位表示。
2. 同一個整數的十六進位表示。
3. 除數，以固定小數位顯示。
4. 當除數不是 `0.0` 時，顯示 `(double)value / divisor` 的結果。
5. 當除數是 `0.0` 時，不進行除法，顯示 `Undefined`。

例如：

```text
Input: 45 2
Decimal: 45
Hex: 2d
Divisor: 2.000
Quotient: 22.500
```

你可以從這些測試開始：

| 輸入 | 你要特別觀察什麼？ |
|---|---|
| `45 2` | 正常十進位、十六進位與除法 |
| `7 3` | 浮點商不是整數 |
| `0 5` | 被除數為零 |
| `45 0` | 必須阻止除以零 |
| 非數字輸入 | `scanf` 是否回報輸入失敗 |
| 接近 `UINT_MAX` 的值 | 型別邊界與格式是否仍正確 |

先寫下預期，再執行。結果不同時，回到「輸入型別 → 運算元型別 → 運算 → 顯示格式」這條路徑逐步追蹤。

如果你使用 `scanf`，也要讓格式與目的型別一致，例如：

```c
unsigned int value;
double divisor;

if (scanf("%u %lf", &value, &divisor) != 2) {
    printf("Invalid input\n");
    return 1;
}
```

這裡的 `&` 已經在前導課程看過；正式的指標模型會在後面的 Unit 完整建立。此時先把它讀成「讓 `scanf` 能把輸入寫進這個變數的位置」即可。

## 12. 再改一次需求，看看哪些地方真的受影響

假設第一版規格把十六進位寫成小寫：

```text
2d
```

現在需求改成：

> 十六進位一律使用大寫字母。

不要重寫整支程式。先找真正和這個需求相連的地方。

在 `printf` 中，`%x` 與 `%X` 就代表不同的十六進位文字格式。修改後，重新執行原本的正常值、零值與邊界案例，確認只有預期的輸出形式改變，而其他行為沒有被破壞。

這是一個很小的需求修改，但它把本章幾件事串在一起：值沒有改、型別沒有改、運算沒有改，改的是**表示方式**。

## 14. 離開這個 Unit 前，試著從程式解釋，而不是背定義

找出前面的程式片段，確認你可以不用背講義文字，直接回答：

- `00101101` 為什麼在「無號二進位整數」的規則下代表 45？
- MSB 與 LSB 是位置名稱，為什麼不能把 MSB 永遠當成正負號位元？
- `double result = a / b;` 中，為什麼左邊的 `double` 不會讓右邊自動保留小數？
- 為什麼 `printf` 的格式字串也是一種型別契約？
- 為什麼 `0.1 + 0.2` 的結果適合用需求導向的容許誤差思考？
- 有號整數溢位和無號整數回繞有什麼本質差別？
- 當結果怪異時，你能不能先判斷它是「有定義但不符合需求」，還是「未定義行為」？

如果某一題只能背一句話回答，就回到相對應的程式，改一個值、做一次預測，再觀察結果。

## 15. 本章收尾

前導課程讓我們先學會追蹤程式在做什麼；這個 Unit 則開始追問更底層的一層：**程式拿到一個值之後，到底用什麼規則解讀與操作它？**

同一組位元要搭配表示規則才有意義；型別決定可用的操作與轉換；運算發生的時間點會影響結果；浮點資料常需要用近似的方式判斷；格式化 I/O 必須讓格式與實際型別一致；到了整數邊界附近，更要先確認語言是否仍然對行為有定義。

下一個 Unit 會把這些判斷帶進更複雜的控制流程。當條件不再只有一個、分支開始巢狀、不同檢查有先後順序時，「哪一個條件先被判斷、哪些狀態能走到哪一條路」會變成新的閱讀與除錯核心。
