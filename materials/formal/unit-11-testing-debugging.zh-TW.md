# 正式單元 F-U11：如何系統化地測試、診斷與改善程式？

版本：1.1.0  
狀態：正式學生教材  
最後更新：2026-08-09  
對應英文版本：[Formal Unit F-U11: How Can Programs Be Tested, Diagnosed, and Improved Systematically?](unit-11-testing-debugging.en.md)

其實我們從很早就一直在測試：

- P-U03 用 99、100、101 看條件邊界。
- F-U03 用最後一個合法索引抓越界。
- F-U08 用配置失敗檢查 ownership。
- F-U09 用格式錯誤、EOF 與超長行測檔案流程。

現在把這些方法收束成一個更完整的問題：

> 程式在某一次輸入得到正確輸出之後，我們還需要哪些證據，才有理由相信它符合需求？

這個 Unit 不會教一個「按下去就證明程式正確」的工具，而是建立一條可以重複使用的證據流程。

---

## 1. 一個成功案例只能證明「這一次成功」

需求：

> 成績必須在 0～100；60 以上為 `Pass`，其餘合法成績為 `Try again`。

只測：

```text
80 → Pass
```

不能告訴我們：

```text
59 呢？
60 呢？
0 呢？
100 呢？
-1、101 呢？
```

所以測試第一步不是「想幾個數字試試看」，而是從需求找出不同類型的行為。

---

## 2. 從需求直接導出測試案例

| 類型 | 輸入 | 預期 |
|---|---:|---|
| 一般通過 | 80 | Pass |
| 及格線下方 | 59 | Try again |
| 及格線 | 60 | Pass |
| 最小合法 | 0 | Try again |
| 最大合法 | 100 | Pass |
| 無效低值 | -1 | Invalid |
| 無效高值 | 101 | Invalid |

每一列都應該能回答：

> 這筆測試對應哪一條需求或哪一個邊界？

這就是 **testing** 的核心：執行程式或元件，把實際結果和事先定義的預期結果比較。

如果預期是在看到程式輸出後才改寫，就失去了很多測試價值。

---

## 3. 測試失敗只告訴你「有不一致」，還沒有告訴你原因

假設程式：

```c
int is_valid_score(int score) {
    return score > 0 && score < 100;
}
```

測試發現：

```text
0   → false，但需求說應合法
100 → false，但需求說應合法
```

此時我們知道程式和需求不一致，但還沒有完成診斷。

**Debugging** 要做的是找出造成不一致的原因。

一個可操作的假設是：

> 上下界使用 `>`／`<`，因此把原本 inclusive 的 0 與 100 排除了。

這比「程式怪怪的」有用，因為它可以被檢查、被反駁，也能指向具體修改。

---

## 4. 一個可靠的 debugging 循環

可以反覆使用：

```text
重現
→ 找第一個不一致
→ 提出原因假設
→ 設計能區分假設的實驗
→ 觀察證據
→ 做最小必要修正
→ 重跑相關測試
```

例如大型程式的最終平均錯了，不要第一步就重寫所有模組。

先找：

```text
檔案讀到的 Student 正確嗎？
StudentList 內容正確嗎？
count 正確嗎？
單獨呼叫 average 函數正確嗎？
```

目標是找到**第一個開始偏離預期的地方**。

---

## 5. Bug report 要讓另一個人可以重現

「程式壞了」不是可用證據。

至少記錄：

- 使用哪個版本／commit。
- 如何建置與執行。
- 輸入或操作步驟。
- 預期結果。
- 實際結果。
- 是否每次發生。
- 相關警告、錯誤訊息或最小重現程式。

越能穩定重現，越容易排除無關因素。

---

## 6. 修好失敗案例後，還沒有結束

假設把：

```c
score > 0 && score < 100
```

改成：

```c
score >= 0 && score <= 100
```

當然要重測 0 和 100。

但還要重跑：

```text
80
59
60
-1
101
```

這叫 **regression testing（回歸測試）**：修改之後，確認原本應該保持不變的行為沒有被破壞。

所以每次修正都要問：

> 哪些案例是這次要改的？哪些案例雖然不該改，卻可能被我的修改波及？

---

## 7. Verification 和 Validation 問的是不同層次

假設程式完全符合這份規格：

```text
0～100 合法
60 以上 Pass
```

### Verification

問：

> 實作有沒有符合已定義的規格？

測試、code review、介面檢查、編譯器診斷都可能提供 verification 證據。

### Validation

再往上一層問：

> 這份規格本身真的是使用者需要的嗎？

如果學校真正規則是 70 分才及格，那一個「完美實作 60 分門檻」的程式仍然不是正確產品。

所以：

```text
Verification：有沒有照規格做？
Validation：規格是不是對的問題？
```

兩者都重要，但不能互相取代。

---

## 8. 測試本身也可能錯

假設手算平均算錯，測試表寫了錯誤預期。

那麼正確程式反而會被標成 failure。

因此有三個東西要分開比較：

```text
需求
→ 預期結果
→ 程式實際結果
```

三者任何一層都可能有錯。

當「實際 ≠ 預期」時，不要自動假設一定是程式碼錯；先確認預期確實來自正確需求。

---

## 9. Refactoring 要靠既有測試保護外部行為

原本：

```c
if (score >= 0) {
    if (score <= 100) {
        return 1;
    }
}
return 0;
```

改成：

```c
return score >= 0 && score <= 100;
```

如果目的只是讓結構更簡潔，而需求行為不應改變，這就是 **refactoring（重構）**。

「看起來等價」仍然不應是唯一證據。

重構前已有的測試應在重構後全部重跑，因為它們現在扮演另一個角色：保護「不應被改變的外部行為」。

---

## 10. Code review 也應提出可以驗證的主張

比較：

```text
這段很醜。
```

和：

```text
這個迴圈使用 i <= length，因此 length == 5 時會存取 values[5]；
最後合法索引是 4。把條件改為 i < length，並加入長度 0、1、5 的邊界測試。
```

第二種 review 比較有用，因為它包含：

```text
位置
→ 風險
→ 原因
→ 可驗證修改
```

Code review 可以持續使用前面所有 Unit 的模型：初始化、邊界、生命週期、ownership、失敗契約、完整輸入、模組依賴。

---

## 11. 自主練習：做一份真正能重現的除錯紀錄

從前面任一 Unit 選一個缺陷。

建立：

1. 一句清楚需求。
2. 最小可重現程式或輸入。
3. 預期與實際結果。
4. 至少兩個可能原因假設。
5. 一個能區分兩個假設的實驗。
6. 根因。
7. 最小修正。
8. 回歸測試表。
9. 一句「為什麼現在比修正前更值得信任」。

最後再標示：哪些證據是在做 verification？是否還需要額外 validation 才知道需求本身正確？

---

## 12. 修改需求：及格線從 60 改成 70

先不要改程式。

第一步先找測試中哪些預期會變：

```text
60 原本 Pass → 現在 Try again
69 → Try again
70 → Pass
100 → 仍然 Pass
0 → 仍然 Try again
-1、101 → 仍然 Invalid
```

接著才修改程式。

最後同時跑：

- 因需求改變而預期改變的案例。
- 預期不應變的 regression cases。

這個順序可以避免「直接改 code，然後再讓測試配合新輸出」。

---

## 13. 選做：讓 AI 挑戰你的證據鏈

這一節完全可以跳過。

先不用任何工具，自己回答：

> 一個測試失敗和一個 bug 根因有什麼不同？Verification 和 validation 又各自需要回答什麼？

如果你想多做一次檢查，可以把自己的 bug hypothesis 交給 AI，請它提出另一個也能解釋現象的原因，再設計一個能區分兩者的實驗。你不需要固定 Prompt，也不需要保存或繳交對話。

AI 提出的原因仍然只是 hypothesis；最後要由可重現實驗與程式證據判斷。

---

## 14. 離開這個 Unit 前，確認你能從需求一路追到證據

直接回答：

- 為什麼一個成功輸出不能證明整個需求？
- 一筆測試案例的預期結果應該從哪裡來？
- Testing 發現的 failure 和 debugging 找到的 root cause 有什麼不同？
- 什麼樣的 debugging hypothesis 才容易被驗證或反駁？
- 為什麼修好失敗案例後仍要跑 regression tests？
- Verification 和 validation 分別在比較哪兩件事？
- 為什麼測試預期本身也必須被審查？
- Refactoring 為什麼需要一組原本就可信的測試保護？

如果答案只剩定義，就選一個真實 bug，從 requirement 開始把整條證據鏈畫一次。

---

## 15. 本章收尾

前十個 Unit 一直在建立各種程式規則；F-U11 把「我們怎麼知道自己真的遵守這些規則」正式整理成方法。

可信度不是來自一次成功，而是來自**需求、預期、測試、可重現失敗、可驗證假設、最小修正與回歸證據**彼此接得起來。

最後一個 Unit 不再新增一個孤立 C 語法主題，而是把前面的資料模型、指標、動態記憶體、檔案、模組與測試全部放進同一個小型應用。重點會是：當多個 Concept 同時存在時，能不能仍然保持每一條責任與證據都說得清楚。
