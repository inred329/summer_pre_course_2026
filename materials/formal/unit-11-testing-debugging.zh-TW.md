版本：1.0.1  
狀態：正式學生教材  
最後更新：2026-08-06

## 文件用途與完成標準

本章供學生獨立閱讀、練習與複習。完成本章代表你能區分 testing、verification、validation 與 debugging，能建立可重現錯誤、縮小範圍、修正並回歸測試，也能用 code review 與 refactoring 改善程式而不改變需求行為。

本章的核心完成標準不依賴 AI。未使用 AI 不影響本章完成、課堂參與或評量；第 14 節是可直接跳過的選用延伸活動。

## 核心問題

> 除了看到正確輸出之外，還需要什麼證據才能信任程式？

完成本章後，你應能：

1. 區分 testing、verification、validation 與 debugging。
2. 由需求建立正常、邊界與錯誤案例。
3. 重現並縮小錯誤範圍。
4. 以假設、證據與實驗進行除錯。
5. 在修正與重構後執行回歸測試。

---

## 1. 一個正確輸出不代表程式可靠

若程式只在輸入 5 時得到正確結果，仍無法知道它在 0、1、負數、上限或格式錯誤時如何表現。

可信度來自多種證據，而不是一次成功。

---

## 2. 四個容易混淆的概念

### Testing

執行程式或元件，觀察實際結果是否符合預期。

### Verification

確認實作是否符合已定義的規格或設計。

> Did we build the program according to the specification?

### Validation

確認需求與完成的程式是否真正解決使用者問題。

> Did we build the right program for the intended need?

### Debugging

當結果不符預期時，定位原因並修正。

測試可以發現不一致；除錯則尋找原因。

---

## 3. 從需求建立測試

需求：輸入 0～100 成績，60 以上輸出 `Pass`，否則 `Try again`；範圍外輸出 `Invalid`。

測試表：

| 類型 | 輸入 | 預期結果 |
|---|---:|---|
| 正常 | 80 | Pass |
| 邊界下方 | 59 | Try again |
| 邊界 | 60 | Pass |
| 最小合法 | 0 | Try again |
| 最大合法 | 100 | Pass |
| 無效低值 | -1 | Invalid |
| 無效高值 | 101 | Invalid |

每一列都應能說明它驗證哪條需求。

---

## 4. 可重現錯誤

好的 bug report 至少包含：

- 使用版本
- 輸入與操作步驟
- 預期結果
- 實際結果
- 是否每次都發生
- 編譯器警告或錯誤訊息

「程式壞了」無法支持診斷。

---

## 5. 除錯循環

```text
重現問題
→ 找到第一個不一致
→ 提出原因假設
→ 設計能區分假設的實驗
→ 觀察證據
→ 修正最可能原因
→ 回歸測試
```

不要同時改很多地方，否則無法知道哪一項修改真正影響結果。

---

## 6. 縮小範圍

可使用：

- 函數測試
- 追蹤表
- 暫時輸出中間狀態
- debugger breakpoint
- 二分縮小輸入或程式區域
- 比較最後正常版本

中間輸出完成後應移除或轉成有控制的診斷機制。

---

## 7. 錯誤案例：測試本身錯了

若預期結果手算錯誤，正確程式也可能被判為失敗。測試資料、預期值與規格本身也需要審查。

比較：

```text
需求
→ 測試預期
→ 程式實際
```

三者任一都可能出錯。

---

## 8. Regression Testing

修正一個錯誤後，除了確認該案例通過，也要重跑原本應正常的案例。

例如修正 `score == 60` 後，不只測 60，也應重新測 59、61、0、100 與無效輸入。

---

## 9. Refactoring

Refactoring 改善程式結構但不改變外部可觀察行為，例如：

- 重新命名
- 拆分函數
- 消除重複
- 簡化條件
- 隔離模組責任

重構前後應使用同一組測試證明行為保持一致。

---

## 10. Code Reading 與 Code Review

審查時可問：

- 需求與介面是否清楚？
- 邊界與失敗路徑是否處理？
- 是否存在未初始化、越界或生命週期風險？
- 名稱是否反映責任？
- 測試是否能證明主張？
- 是否有不必要複雜度？

審查結論應指出具體程式位置、風險與可驗證修改，而不是只說「不好」。

---

## 11. 引導練習

取得一段含兩個缺陷的成績程式：

1. 先用測試表重現。
2. 找第一個不一致狀態。
3. 每次只修正一項。
4. 重跑全部案例。
5. 寫下證據鏈。

---

## 12. 自主練習：除錯報告

選擇先前 Unit 的一個錯誤案例，建立：

- 最小重現程式
- 預期與實際結果
- 至少兩個原因假設
- 區分假設的實驗
- 修正
- 回歸測試表
- 一段簡短根因說明

---

## 13. 需求修改

原程式只處理整數成績，現在改成小數。更新規格、型別、格式、邊界測試與浮點比較方式，再確認舊整數案例仍成立。

---

## 14. 選用延伸：使用 AI 檢查自己的解釋

本節可以直接跳過，不屬於核心完成條件，也不需要固定 Prompt、保存或繳交對話，未使用時不需要任何聲明。

若你選擇使用 AI，可以先用自己的話解釋：

> Testing、verification、validation 與 debugging 有什麼差異？為什麼一次正確輸出不足以證明程式可靠？

再把 AI 回應與規格、測試表、失敗案例及可重現結果逐項比較。若內容衝突，應以可驗證證據重新判斷，而不是把 AI 回應視為答案。

## 16. 本章摘要

可信程式需要需求、預期、測試、追蹤與可重現證據。Testing 找出不一致，verification 對照規格，validation 對照真正需求，debugging 定位並修正原因。下一章將整合所有 Concept 完成一個可維護的小型應用。
