# 正式單元 F-U02：如何建立可靠的多分支與重複流程？

版本：1.1.0  
狀態：正式學生教材  
最後更新：2026-08-09  
對應英文版本：[Formal Unit F-U02: How Can Reliable Multi-Branch and Repetitive Flows Be Built?](unit-02-complex-control-flow.en.md)

F-U01 讓我們看到：同一段程式只要型別、表示方式或運算時機不同，結果就可能改變。

接下來再往前一步。當程式不只「算一個結果」，而是要根據資料走不同路徑時，新的問題出現了：

> 如果條件愈來愈多、分支開始巢狀、輸入筆數又不固定，我們要怎麼知道每一條路都真的可靠？

這一個 Unit 不會只增加更多 `if` 與迴圈語法。我們會一直追問三件事：**現在有哪些可能路徑？每條路在什麼條件下發生？我們要用什麼測試證明沒有漏掉重要情況？**

---

## 1. 先從一個看似簡單的成績分類開始

看下面的程式：

```c
int score = 85;

if (score >= 90) {
    printf("A\n");
} else if (score >= 80) {
    printf("B\n");
} else if (score >= 70) {
    printf("C\n");
} else {
    printf("D\n");
}
```

先不要執行。從第一個條件開始往下追蹤：

1. `85 >= 90` 是 false，所以繼續。
2. `85 >= 80` 是 true，所以輸出 `B`。
3. 一旦某個分支成立，後面的 `else if` 就不再檢查。

這裡真正重要的不是「會寫 `else if`」，而是：**分支的排列順序本身就是規則的一部分。**

例如把條件改成：

```c
if (score >= 70) {
    printf("C or above\n");
} else if (score >= 90) {
    printf("A\n");
}
```

對 `95` 而言，第一個條件已經成立，所以第二個 `score >= 90` 根本走不到。

程式可以編譯，條件也都合法，但規則被排壞了。

---

## 2. 邊界值最容易揭露分支規則

如果等第規則是：

- 90 以上為 A
- 80～89 為 B
- 70～79 為 C
- 其餘為 D

那麼只測 `85` 遠遠不夠。

至少應該看這些值：

| `score` | 預期結果 | 為什麼重要？ |
|---:|---|---|
| 69 | D | C 的下方 |
| 70 | C | C 的起點 |
| 79 | C | B 的前一格 |
| 80 | B | B 的起點 |
| 89 | B | A 的前一格 |
| 90 | A | A 的起點 |

這些數字不是隨便挑的。它們貼著規則切換的位置，可以很快找出 `>`／`>=` 寫錯、分支順序寫錯或某一段範圍沒有涵蓋的問題。

所以之後遇到多分支時，可以先問：

> 規則在哪些值上會改變？那些位置的前一個值、邊界值與後一個值分別會走哪裡？

---

## 3. `switch` 是另一種「選路」，但適合的問題不同

假設現在不是判斷成績範圍，而是處理選單：

```text
1 = Add
2 = Delete
其他 = Unknown
```

這種「同一個值等於哪一個離散選項」的情況，可以用：

```c
switch (command) {
    case 1:
        printf("Add\n");
        break;
    case 2:
        printf("Delete\n");
        break;
    default:
        printf("Unknown\n");
}
```

`switch` 很適合整數型或列舉型值的離散選擇；像 `score >= 90` 這種範圍條件，仍然比較適合 `if`。

這裡還有一個容易忽略的控制流程：`break`。

如果寫成：

```c
case 1:
    printf("One\n");
case 2:
    printf("Two\n");
```

當 `command == 1` 時，執行完 `case 1` 之後會繼續落入 `case 2`。這叫做 **fall-through**。

Fall-through 本身不是語法錯誤；有時甚至是刻意設計。但如果需求只允許一個動作，漏掉 `break` 就是邏輯錯誤。若是刻意 fall-through，也應讓讀程式的人一眼看得出原因。

---

## 4. 巢狀條件不是「更多 if」，而是更多路徑組合

再看會員折扣：

```c
if (is_member) {
    if (amount >= 1000) {
        discount = 0.15;
    } else {
        discount = 0.10;
    }
} else {
    discount = 0.0;
}
```

不要只從縮排閱讀。把它翻成路徑：

| `is_member` | `amount` | 預期折扣 |
|---|---:|---:|
| false | 1500 | 0.00 |
| true | 999 | 0.10 |
| true | 1000 | 0.15 |

第一列也提醒一件事：當 `is_member` 是 false 時，`amount >= 1000` 根本不需要被拿來決定折扣。

因此遇到巢狀條件，與其只盯著大括號，更可靠的做法是先把「哪些條件組合真的能走到某個結果」列出來。

這也是之後設計測試時很實用的方法：**測的是可到達的路徑，不是每個 `if` 各挑一個 true 就算完成。**

---

## 5. 當同一個判斷要一直重複，問題就從分支走進迴圈

目前為止，每個例子都只處理一次資料。

但假設你要讓使用者持續輸入整數並加總，而且不知道一開始會有幾筆。這時固定寫五次 `scanf` 當然不合理，我們需要重複流程。

先定義一個協定：

> 使用者輸入 `-1` 表示「資料結束」。

這個特殊值稱為 **sentinel（哨兵值）**。

完整例子：

```c
#include <stdio.h>

int main(void) {
    int value;
    int sum = 0;

    while (scanf("%d", &value) == 1) {
        if (value == -1) {
            printf("Sum: %d\n", sum);
            return 0;
        }

        sum += value;
    }

    if (feof(stdin)) {
        fprintf(stderr, "Input ended before sentinel\n");
    } else {
        fprintf(stderr, "Invalid input\n");
    }

    return 1;
}
```

先沿著三種不同輸入走一次。

### 情況 A：正常遇到 sentinel

```text
5 8 2 -1
```

`5`、`8`、`2` 被加入 `sum`，`-1` 只代表「結束」，不加入總和。

### 情況 B：先遇到 EOF

如果輸入來源在 `-1` 之前就結束，`scanf` 不會成功讀到下一個整數。這不是 sentinel；它表示輸入來源已經沒有更多資料。

### 情況 C：遇到無效文字

```text
5 8 hello
```

`hello` 不能依 `%d` 轉成整數，所以轉換失敗。這也不是 sentinel，更不是 EOF。

因此：

> **sentinel 是一筆具有特殊意義的合法資料；EOF 是輸入來源結束；無效文字是格式轉換失敗。三者不能混成同一件事。**

---

## 6. 為什麼迴圈條件要直接檢查 `scanf` 的結果？

你可能看過這種寫法：

```c
scanf("%d", &value);
while (value != -1) {
    sum += value;
    scanf("%d", &value);
}
```

它看起來比較短，但把一件非常重要的資訊丟掉了：**這一次讀取到底有沒有成功？**

如果第一次轉換就失敗，`value` 並沒有取得這次輸入所提供的有效整數；若後續轉換失敗，舊值又可能留在變數裡，使程式重複處理先前的資料。

所以可靠的輸入迴圈通常讓「讀取成功」直接成為是否進入本輪處理的條件：

```c
while (scanf("%d", &value) == 1) {
    /* 此處才使用 value */
}
```

這和前導課程建立的原則完全一致：**先確認輸入成功，再使用值。**

---

## 7. Loop invariant：替迴圈找一個「每輪都不能被破壞的事實」

迴圈比單次 `if` 難驗證的一個原因，是同一段程式會執行很多次。

與其試著一次想完整個迴圈，可以先抓住一個每輪都成立的事實。

以上面的加總程式為例，在每次成功讀到 `value`、準備處理它時，可以主張：

> `sum` 等於目前這一筆之前，所有已接受且不是 sentinel 的輸入總和。

這樣的敘述叫做 **loop invariant（迴圈不變量）**。

不要急著把 invariant 背成定義。用它檢查三件事就好：

1. **開始以前成立嗎？** 還沒有任何資料時，`sum == 0`。
2. **處理一筆正常資料後還成立嗎？** 把這筆值加進 `sum`，下一輪開始時它就成為「之前已接受的資料」之一。
3. **遇到 sentinel 時能得到我們要的結果嗎？** Sentinel 不加入總和，因此此刻的 `sum` 正好是所有有效資料的總和。

如果這三步能說清楚，你就不只是「看起來覺得迴圈會動」，而是開始能解釋它為什麼維持正確狀態。

---

## 8. 把錯誤放回它破壞的規則來看

現在重新看幾個常見錯誤，它們就不需要變成另一張要背的清單。

### Sentinel 被加入總和

如果先做：

```c
sum += value;
```

再判斷 `value == -1`，那麼 sentinel 已經污染 `sum`。這破壞了「`sum` 只包含非 sentinel 值」的 invariant。

### 漏掉 `break`

如果選單需求一次只能執行一個動作，fall-through 會讓一條路徑意外進入下一條路徑。

### 巢狀條件只測最順的一條路

只測 `true/true`，不能證明 `false` 路徑或 999／1000 這些邊界正確。這不是編譯器錯誤，而是你的證據還不完整。

### 輸入失敗後仍使用舊值

這破壞了「每一輪處理的 `value` 都來自一次成功讀取」這個前提。問題的根源不是 `while` 本身，而是資料進入流程以前沒有先驗證。

當你能指出「哪一個規則被破壞」，除錯通常會比只記錯誤名稱容易得多。

---

## 9. 先做兩個小練習，把路徑畫清楚

### 練習 A：離散選單

建立簡單選單：

```text
1 = Query
2 = Modify
0 = Exit
其他 = Invalid
```

在寫 `switch` 以前，先列出四類可能路徑。使用 `command` 以前先確認 `scanf` 成功。

完成後故意拿掉一個 `break`，預測哪一個輸入會多做一個動作，再實際驗證。

### 練習 B：會員折扣

沿用前面的會員折扣規則，先不要寫更多程式。

先回答：

- 非會員會不會需要檢查消費是否滿 1000？
- `amount == 999` 走哪條路？
- `amount == 1000` 走哪條路？

如果這三題能從路徑表回答，再開始寫程式。

---

## 10. 自主練習：不知道會有幾筆成績時怎麼算平均？

現在把前面的 sentinel 加總改成比較完整的問題。

持續讀入 `0`～`100` 的成績，以 `-1` 表示輸入結束，最後輸出：

- 有效成績筆數
- 有效成績平均

先不要急著寫完整程式。先定義：

> 每一輪開始時，`count` 與 `sum` 分別代表什麼？

接著至少走過這些案例：

| 輸入情況 | 要觀察的風險 |
|---|---|
| 一筆資料後 `-1` | 基本計數與平均 |
| 多筆資料後 `-1` | 重複更新是否一致 |
| 一開始就是 `-1` | `count == 0`，不可除以零 |
| `0` 與 `100` | 合法範圍邊界 |
| 無效文字 | 不可當作 sentinel |
| sentinel 前 EOF | 必須和正常結束區分 |
| 超出範圍的數字 | 需求尚未定義，要先做決策 |

最後一列故意留下了一個規格問題：如果讀到 `120`，到底要拒絕、忽略，還是終止？

程式不能替需求做沒有說明的猜測。

---

## 11. 修改需求：忽略超出範圍的數字

現在把上一節留下的問題補完整：

> 小於 0 或大於 100 的一般數值都忽略，但 `-1` 仍然代表結束；無效文字與 EOF 仍照原本方式處理。

注意 `-1` 同時小於 0，所以檢查順序很重要。

如果你先寫：

```c
if (value < 0 || value > 100) {
    continue;
}
```

那 `-1` 會先被當成「忽略」，程式永遠收不到結束訊號。

因此你需要先辨認 sentinel，再判斷一般資料範圍。

修改後，重新回答：

- `sum` 的 invariant 有沒有改？
- `count` 什麼時候增加？
- `-1`、`120`、`hello`、EOF 分別走哪條路？
- 原本所有正常案例是否仍然通過？

這就是一次小型回歸測試：新規則加入以後，舊的正確行為不能被不小心破壞。

---

## 12. 選做：讓 AI 挑戰你的路徑解釋

這一節完全可以跳過。

先不用任何工具，自己回答：

> 為什麼分支順序會改變結果？`-1`、EOF、無效文字與 loop invariant 分別代表什麼？

如果你想多做一次檢查，可以把自己的解釋交給 AI，請它找出你是否混淆了資料、輸入狀態或迴圈保證。你不需要固定 Prompt，也不需要保存或繳交對話。

如果 AI 的回答和路徑表、`scanf` 回傳規則、實際追蹤或可重現結果衝突，就回到這些證據重新判斷。

---

## 13. 離開這個 Unit 前，確認你真的會「走路徑」

回到本章的程式，不看摘要，試著直接回答：

- 為什麼 `if`／`else if` 的排列順序會改變程式行為？
- 為什麼 79、80、89、90 比只測 85 更能驗證等第規則？
- 什麼情況適合 `switch`，什麼情況仍適合 `if`？
- 為什麼巢狀條件要看「可到達的組合」，而不是只數有幾個 `if`？
- 為什麼 sentinel、EOF 與無效輸入是三件不同的事？
- 為什麼 `scanf` 的成功與否應該在使用 `value` 以前確認？
- 你能不能用自己的話說出加總迴圈的 invariant，並解釋它如何被初始化、維持與用來得出結果？
- 當需求改成忽略超出範圍的值時，為什麼 `-1` 的檢查順序變得重要？

如果某一題只能背一句話回答，就回到對應範例，換一組輸入，自己走一次路徑。

## 14. 本章收尾

F-U01 關心「一個值如何被表示、解讀與運算」；這個 Unit 再把問題推進到「這個值會讓程式走哪一條路，而且這條路是否可靠」。

多分支的可靠性來自正確的條件順序與邊界測試；巢狀流程要看真正可到達的路徑組合；重複輸入除了要有終止規則，也要保留讀取成功與否；loop invariant 則讓我們能說明狀態如何在一次又一次迭代中保持正確。

下一個 Unit 會改變資料本身的規模。現在我們已經能可靠地重複處理一筆又一筆資料，但如果五個、五十個、五百個同類資料都需要同時保留下來，再用 `score1`、`score2`、`score3` 一個個命名就會開始失控。這正是陣列要解決的問題。
