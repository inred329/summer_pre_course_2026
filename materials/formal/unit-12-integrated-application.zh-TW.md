# 正式單元 F-U12：如何完成跨 Concept 的整合程式？

版本：1.0.0  
狀態：正式學生教材  
最後更新：2026-08-04  
對應英文版本：[Formal Unit F-U12: How Can a Program Integrate Concepts Across the Course?](unit-12-integration.en.md)

## 文件用途與完成標準

本章供學生獨立閱讀、實作與複習。完成本章代表你能把需求、資料、控制流程、函數、記憶體、檔案、模組與測試整合成一個可解釋、可修改、可驗證的小型 C 應用。

## 核心問題

> 如何把需求、資料、控制、函數、記憶體、互動與工程能力整合成一個可信的程式？

完成本章後，你應能：

1. 從需求建立資料模型與模組責任。
2. 定義介面、資料流與錯誤處理。
3. 建立可逐步驗證的最小版本。
4. 使用測試、除錯與回歸控制修改風險。
5. 說明設計選擇、限制與維護方式。

---

## 1. 綜合案例：個人成績管理器

系統需求：

- 新增學生與成績
- 顯示所有學生
- 依學號查詢
- 計算平均與及格狀態
- 儲存到文字檔
- 啟動時讀回資料
- 處理無效輸入與檔案錯誤

本章重點不是功能越多越好，而是每一項功能都能被理解、測試與修改。

---

## 2. 從需求到 Concept

```text
需求
├── 資料：Student 結構與集合
├── 控制：選單、查詢、重複操作
├── 抽象：新增、查詢、統計函數
├── 記憶體：固定或動態容量
├── 互動：輸入、輸出、檔案格式
└── 工程：模組、測試、錯誤處理
```

每個設計選擇都應能對應到一個需求或風險。

---

## 3. 資料模型

```c
typedef struct {
    int id;
    char name[40];
    double score;
} Student;

typedef struct {
    Student *items;
    int size;
    int capacity;
} StudentList;
```

請先定義 invariant：

```text
0 <= size <= capacity
items 在 capacity > 0 時指向足夠空間
前 size 個元素為有效資料
```

---

## 4. 模組責任

```text
student.h / student.c
- Student 與基本驗證

student_list.h / student_list.c
- 動態集合、查詢、新增、釋放

storage.h / storage.c
- 檔案讀寫與格式

main.c
- 選單與流程協調
```

`main` 不應直接操作所有內部細節；它依賴模組介面。

---

## 5. 先建立垂直切片

不要一次完成所有功能。第一個可執行版本可以只做：

```text
建立空清單
→ 新增一位學生
→ 顯示該學生
→ 正確釋放記憶體
```

確認資料流與所有權後，再加入查詢、檔案與統計。

---

## 6. 介面草案

```c
int list_init(StudentList *list);
void list_destroy(StudentList *list);
int list_append(StudentList *list, Student student);
Student *list_find_by_id(StudentList *list, int id);
double list_average(const StudentList *list);
int save_students(const StudentList *list, const char *path);
int load_students(StudentList *list, const char *path);
```

每個介面都應說明：

- 前置條件
- 會修改哪些物件
- 成功與失敗回傳
- 所有權是否改變
- 空集合與錯誤輸入行為

---

## 7. 測試策略

### 單元測試方向

- 空清單平均
- 新增第一筆
- 容量成長
- 重複學號
- 查詢不存在學號
- 儲存後再載入
- 檔案格式錯誤
- 配置失敗路徑（以設計與可測替代方式討論）

### 整合測試方向

```text
新增資料
→ 儲存
→ 結束程式
→ 重新啟動
→ 載入
→ 查詢與統計結果一致
```

---

## 8. 錯誤處理

不要只輸出 `Error`。區分：

- 無效使用者輸入
- 重複資料
- 找不到資料
- 配置失敗
- 檔案不存在
- 檔案格式錯誤
- 寫入失敗

不同錯誤可能需要不同回復策略，而非全部終止程式。

---

## 9. 錯誤案例

### 模組邊界被破壞

`main.c` 直接修改 `list.capacity` 或重新配置 `items`，使所有權分散。應透過模組介面操作。

### 儲存格式與讀取格式不一致

寫入欄位順序和讀取假設不同。建立一份格式規格與 round-trip 測試。

### 修改功能後沒有回歸

加入排序後，查詢或儲存可能改變。所有既有測試仍需執行。

### 成功路徑才釋放資源

中途錯誤返回時漏掉檔案關閉或記憶體釋放。設計統一 cleanup 流程。

---

## 10. 引導實作順序

1. 完成資料結構與 invariant。
2. 完成初始化、釋放與新增。
3. 完成查詢與顯示。
4. 完成統計。
5. 定義檔案格式並完成儲存。
6. 完成載入與錯誤處理。
7. 加入選單。
8. 執行完整回歸。

每一步都應保持可編譯、可執行與有測試。

---

## 11. 需求修改

選擇一項修改：

- 一位學生可有多次成績
- 新增排序
- 新增刪除功能
- 支援 CSV 格式
- 顯示統計分布

修改前先寫影響分析：資料模型、介面、檔案格式、測試與相容性哪些需要改變。

---

## 12. 說明與維護文件

程式完成時應能回答：

- 核心需求與限制是什麼？
- 資料模型與 invariant 是什麼？
- 各模組責任是什麼？
- 檔案格式是什麼？
- 如何編譯與執行？
- 如何重現主要測試？
- 已知限制與下一步是什麼？

文件不是最後裝飾，而是介面與維護的一部分。

## 15. 本章摘要

整合程式不是把語法堆在一起，而是讓需求、資料、流程、介面、生命週期、持久化與證據互相一致。可靠的工程流程讓每次修改都有可追蹤影響與回歸保護。完成本 Unit 後，你應能以自己的程式說明整門課的 Concept 如何共同工作。
