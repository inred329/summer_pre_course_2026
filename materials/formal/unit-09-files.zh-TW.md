# 正式單元 F-U09：程式如何與檔案及持久資料互動？

版本：1.2.0  
狀態：正式學生教材  
最後更新：2026-08-10  
對應英文版本：[Formal Unit F-U09: How Does a Program Interact with Files and Persistent Data?](unit-09-files.en.md)

F-U08 讓資料可以在程式執行期間依需求取得空間，但 `malloc` 配置的物件仍然只活在這次程式執行裡。

如果我們希望今天輸入的學生資料，在明天重新啟動程式後還能讀回，就需要把資料交給程式外部的持久儲存。

最基本的做法就是檔案。

寫檔不是「把變數搬到硬碟」這麼簡單。程式需要先和檔案建立一條可以讀寫的連結。C 標準 I/O 會把這種連結與它目前的讀寫狀態一起看成一個 **stream（資料流）**。現在可以先把 stream 理解成「程式目前用來和某個輸入／輸出來源交換資料的通道與狀態」；下一節再看 `FILE *` 怎麼代表它。

除了 stream，程式還需要明確的開啟模式、共同格式，以及每一步的成功／失敗判斷。

這個 Unit 會沿著一筆成績資料的完整旅程來看這些問題。

---

## 1. 先把一個數字真的寫進檔案

```c
#include <stdio.h>

int main(void) {
    FILE *file = fopen("scores.txt", "w");
    if (file == NULL) {
        perror("scores.txt");
        return 1;
    }

    if (fprintf(file, "%d\n", 80) < 0) {
        fprintf(stderr, "Write failed\n");
        fclose(file);
        return 1;
    }

    if (fclose(file) == EOF) {
        fprintf(stderr, "Close failed\n");
        return 1;
    }

    return 0;
}
```

先把流程看成：

```text
fopen
→ 得到 FILE *，代表目前開啟的 stream
→ fprintf 透過 stream 寫入
→ fclose 完成並關閉 stream
```

`FILE *` 是標準函式庫提供給我們操作 stream 的型別。它讓函式庫保存這次開啟所需要的狀態，例如目前的讀寫位置與錯誤狀態；你不需要知道 `FILE` 內部實際長什麼樣。

這裡先把兩個東西分開：

```text
scores.txt        檔案本身，可以在程式結束後繼續存在
FILE *file        這次程式執行中，用來操作該檔案 stream 的物件
```

因此每個成功 `fopen` 都要有對應的使用與關閉路徑。

---

## 2. 開檔模式本身就是資料政策

最常見的文字模式：

```text
"r"  讀取既有檔案
"w"  寫入；若檔案已存在會截斷舊內容
"a"  寫入尾端；保留既有內容
```

如果需求是「新增今天的紀錄」，卻使用 `"w"`，程式可能在第一步就把昨天的資料清掉。

所以模式不只是函式用法的細節，而是需求的一部分：

> 這次執行要讀取、覆蓋，還是附加？

也不要把「`fopen` 成功」誤解成「整個寫檔一定成功」。後面的 `fprintf` 與最後 `fclose` 都有自己的失敗可能。

---

## 3. 讀檔迴圈應該由「這次有沒有讀到資料」控制

現在把剛才的整數讀回：

```c
#include <stdio.h>

int main(void) {
    FILE *file = fopen("scores.txt", "r");
    if (file == NULL) {
        perror("scores.txt");
        return 1;
    }

    int score;
    int result;

    while ((result = fscanf(file, "%d", &score)) == 1) {
        printf("%d\n", score);
    }

    /* 下面再判斷為什麼停止 */

    fclose(file);
    return 0;
}
```

這和前面處理 `scanf` 的原則完全一致：

> **先由讀取函數的回傳結果決定這一次是否真的取得一筆有效資料，再使用輸出變數。**

不要先寫：

```c
while (!feof(file)) {
    fscanf(file, "%d", &score);
    /* 使用 score */
}
```

EOF 狀態通常是在一次讀取嘗試遇到結尾後才被觀察到；如果先用 `feof` 猜「下一次還有沒有資料」，很容易多處理一次舊值。

---

## 4. 讀取停止後，再分類「為什麼停」

對：

```c
fscanf(file, "%d", &score)
```

常見結果：

- `1`：成功完成一個 `%d` 轉換。
- `0`：目前還有輸入，但下一段內容不符合 `%d`。
- `EOF`：在完成轉換以前遇到檔案結尾或輸入錯誤。

所以迴圈結束後：

```c
if (result == EOF) {
    if (ferror(file)) {
        fprintf(stderr, "Read error\n");
        /* I/O 錯誤 */
    } else {
        /* 正常 EOF */
    }
} else {
    fprintf(stderr, "Invalid score format\n");
}
```

這三種情況不能混在一起：

```text
正常讀完
格式不符合
真正的 I/O 錯誤
```

尤其 `result == 0` 時，造成失敗的字元通常還留在 stream 中。如果什麼都不處理就重做同一個 `%d` 轉換，程式可能一直卡在同一段資料。

---

## 5. 如果一筆資料是一整行，先確保真的拿到完整行

F-U04 已經看過 `fgets` 的容量問題；檔案也完全一樣。

```c
char line[100];

while (fgets(line, sizeof line, file) != NULL) {
    printf("%s", line);
}
```

一次成功 `fgets` 只保證取得一段以 `\0` 結束的字串，不保證這段就是完整的邏輯紀錄。

如果緩衝區在換行以前就滿了，同一個實體行的剩餘字元會留到下一次呼叫。

可以先檢查：

```c
#include <string.h>

if (strchr(line, '\n') == NULL && !feof(file)) {
    fprintf(stderr, "Line exceeds buffer\n");
}
```

這可以抓出常見的「還沒讀到換行，stream 也還沒到 EOF」情況。

最後一行若合法地以 EOF 結束而沒有換行，則是另一種情況。真正負責把輸入文字拆成合法紀錄的程式（**parser，解析器**）必須自己定義：

- 最後無換行的一行是否接受？
- 超長行要丟棄、組合多個片段，還是整筆失敗？

不能默默把前半段當成完整紀錄。

---

## 6. 檔案格式其實是一個 protocol

假設檔案內容是：

```text
1001 Amy 87.5
1002 Ben 91.0
```

讀取端會假設：

```text
第一欄 = id
第二欄 = name
第三欄 = average
```

這就是一個簡單 **protocol（約定）**：寫入端和讀取端都同意每一欄代表什麼、資料怎麼排列。

一旦需求說「姓名可能包含空白」，例如：

```text
1003 Mary Jane 88.0
```

原本單純以空白分隔的格式就不再足夠。

這提醒我們：

> 檔案不是自動懂得 struct 的欄位。寫入端和讀取端必須對序列化格式有共同約定。

格式變更也要像其他對外約定的變更一樣有意識地處理。

---

## 7. 載入多筆資料時，不要讓半份失敗資料污染正式狀態

假設我們要從檔案建立學生陣列。

一個常見風險是：前五筆都已經直接寫進正式資料，第六筆格式錯誤，函數才回報失敗。此時呼叫者得到「載入失敗」，但正式資料已被改了一半。

更容易推理的策略是：

```text
讀進暫存狀態
→ 每筆都驗證
→ 全部成功
→ 才提交成正式結果
```

這和 F-U08 的 `realloc`／`append_value` 很像：**可能失敗的工作先在暫存狀態完成，成功後才提交。**

如果需求允許「遇到壞資料就保留前面成功的紀錄」，也可以，但這必須是明確政策，而不是錯誤處理的偶然副作用。

---

## 8. 寫檔也有一條完整失敗路徑

成功開啟不代表成功保存。

至少要考慮：

```text
fopen 失敗
fprintf / fwrite 失敗
最後 fclose 失敗
```

例如：

```c
if (fprintf(file, "%d\n", score) < 0) {
    fprintf(stderr, "Write failed\n");
    /* 處理後仍要關閉已開啟的 stream */
}
```

最後：

```c
if (fclose(file) == EOF) {
    fprintf(stderr, "Close failed\n");
}
```

因為標準 I/O 可能有緩衝，部分錯誤可能到 flush／close 時才真正被觀察到。

所以「成功開檔」只是開始，不是成功保存的證明。

---

## 9. 把常見檔案錯誤放回流程

### 用錯模式

想附加卻使用 `"w"`：資料在處理內容以前就可能被截斷。

### 不檢查 `fopen`

後面拿 `NULL` 的 `FILE *` 當有效 stream 使用。

### 用 `while (!feof(file))`

用「上一次是否已經看到 EOF」猜下一次讀取，容易重複處理舊資料。

### 把格式失敗當正常 EOF

錯誤 token 還留在 stream，程式卻假裝檔案正常結束。

### 把 `fgets` 片段當完整紀錄

一個長行被拆成兩次讀取，結果錯誤變成兩筆資料。

### 忽略寫入／關閉結果

程式印出「Saved」，但實際持久化並沒有被驗證。

這些錯誤都可以放回同一條路徑找位置：

```text
開啟 → 取得完整紀錄 → 解析／驗證 → 處理 → 寫入 → 關閉
```

## 10. 自主練習：成績檔案報告

設計一個文字檔，保存多筆：

```text
學號 姓名 成績
```

程式讀取後輸出：

- 有效紀錄筆數
- 平均
- 最高分

先定義格式限制。例如若姓名不能包含空白，就明確寫進規格；如果要允許空白，就改用你能可靠解析的格式。

至少測試：

| 情況 | 要確認什麼？ |
|---|---|
| 檔案不存在 | `fopen` 失敗路徑 |
| 空檔案 | 0 筆資料如何定義 |
| 正常多筆 | 基本流程 |
| 一筆格式錯誤 | 不能被當成 EOF |
| 一行超過緩衝區 | 不能把片段當完整紀錄 |
| 最後一行無換行 | 是否依規格接受 |
| 中途失敗 | 正式結果是否維持你定義的提交政策 |

---

## 11. 修改需求：把分析結果寫到 `report.txt`

現在不只讀資料，還要保存報告。

先決定：

> 每次執行要覆蓋上次報告，還是附加新的執行結果？

這直接決定 `"w"` 或 `"a"`。

再定義：

- 開啟輸出檔失敗怎麼辦？
- 某次 `fprintf` 失敗怎麼辦？
- `fclose` 失敗時程式是否仍回報成功？
- 輸入檔成功、輸出檔失敗時整體 exit status 是什麼？

不要只讓「看起來有 report.txt」成為成功判斷。

## 12. 選做：讓 AI 挑戰你的檔案狀態圖

這一節完全可以跳過。

先不用任何工具，自己回答：

> `fscanf` 為什麼應該由回傳值控制迴圈？一次讀取停止後，怎麼分辨正常 EOF、格式錯誤與 I/O 錯誤？

如果你想多做一次檢查，可以讓 AI 為你的檔案格式設計一筆「看似正常但會破壞 parser 假設」的資料。你不需要固定 Prompt，也不需要保存或繳交對話。

如果它的說法和函式回傳規格、實際測試檔或可重現結果衝突，就回到證據重新判斷。

## 13. 離開這個 Unit 前，確認你能追蹤一筆資料的完整旅程

直接回答：

- stream 和檔案本身有什麼不同？`FILE *` 在這段關係中代表什麼？
- 為什麼 `"w"`／`"a"` 是需求決策，不只是語法？
- 為什麼成功 `fopen` 不代表最後寫檔成功？
- `fscanf(... "%d" ...)` 回傳 `1`、`0`、`EOF` 分別意味什麼？
- 為什麼不應該先用 `feof` 猜下一次讀取會不會成功？
- `fgets` 成功時，為什麼目前 buffer 仍可能只是某一行的片段？
- 檔案格式為什麼可以視為 writer 與 reader 之間的 protocol？
- 為什麼「暫存完整載入，成功後再提交」會比半途修改正式狀態更容易推理？
- 為什麼 `fclose` 的結果也值得檢查？

如果回答只剩函式名稱，就從「開啟」開始畫到「關閉」，把 stream 與每個可能失敗的位置一起標出來。

---

## 14. 本章收尾

F-U08 管理的是程式執行期間的物件生命週期；F-U09 把資料生命延伸到程式結束以後。

可靠檔案處理不是只會 `fopen` 和 `fclose`，而是維持完整流程：**建立並管理 stream、選對模式、取得完整紀錄、由讀取結果判斷狀態、遵守格式 protocol、明確提交失敗政策、檢查寫入與關閉。**

下一個 Unit 會處理程式本身逐漸變大的問題。當檔案讀寫、學生資料、動態陣列與分析功能全部放在同一個 `.c` 檔裡，修改一個功能會開始影響整片程式。我們需要把「對外介面」和「內部實作」分開，進入模組化程式設計。
